## 2. S9-1 — критичные исправления корректности и безопасности

### 2.1. Редактор источников `/sources`

Исправить:

- HTML-инъекцию в HTMX-ответе проверки подключения: имя источника и ошибка
  выводятся через `fmt.Fprintf` без экранирования
  (`internal/web/sources.go:192-193`);
- неполную валидацию итогового YAML: `SourceEditor.ValidateAll` делает strict
  decode, но не вызывает полную `Connections.Validate`
  (`internal/config/sourceedit.go:118-131`);
- потерю параллельных правок: сериализовать сохранение mutex'ом либо добавить
  optimistic revision; временные файлы должны быть уникальными;
- игнорирование ошибки аудита: изменение не должно оставаться без записи в
  hash-chain (`internal/web/sources.go:25-31`);
- рассинхронизацию файла и hot-apply: при ошибке применения откатить файл либо
  восстановить согласованное состояние; не сообщать, что невалидный для старта
  конфиг просто «вступит после рестарта»;
- слабую проверку секрета: строка `plaintext${X}` не должна считаться
  ENV-ссылкой (`internal/config/sourceedit.go:248-279`);
- невозможность редактировать существующие Vault `ref` и per-source лимиты
  `max_concurrent_scans`, `max_concurrent_tables`, `query_timeout_s`.

Приёмка: негативные тесты XSS/секретов/схемы, конкурентное сохранение,
fail-closed аудит, rollback hot-apply, round-trip Vault и лимитов, race-тесты.

### 2.2. Полное имя таблицы

Сейчас в verdict ID, `scan_tables` и вердиктах используется только `t.Name`
(`internal/scanengine/engine.go:700-707`). Одноимённые таблицы из разных схем
могут конфликтовать и неправильно обрабатываться при resume.

Перевести конвейер на qualified name `schema.table`: коннекторы, движок,
чекпоинты, verdict ID, store, дрейф, API/UI и будущее описание БД. Добавить
forward-миграцию и тесты с одинаковыми именами таблиц в разных схемах.

### 2.3. Совместимость resume и provenance

`scan -resume` сейчас выбирает последний partial/interrupted прогон и пропускает
done-таблицы без обязательной сверки версий (`cmd/zond/main.go:283-294`).

Сохранять в `scans` и проверять перед продолжением:

- `config_fingerprint`;
- `taxonomy_version`;
- `detectors_version`;
- версию бинарника;
- версию базового промпта и хэш пользовательского промпта после S9-3.

При несовпадении — отказ с перечнем различий. Добавить resume в REST API и UI,
сохранив существующий CLI-сценарий.

## 3. S9-2 — результат LLM по каждому столбцу

Итоговый вердикт по колонке уже существует, но он может отличаться от ответа
LLM. В `evidence.llm` сейчас сохраняются преимущественно `reason_ru`, agent и
model (`internal/scanengine/engine.go:781-795`).

Необходимо раздельно сохранять и показывать:

- итоговый вердикт ансамбля;
- ответ классификатора: label, confidence, sensitivity, reason_ru;
- ответ верификатора;
- agent/model, prompt version/hash;
- tokens, cost, latency;
- тип операции `classify|verify`;
- состояние LLM-обработки: `called`, `not_called`, `small_sample`, `cache_hit`,
  `cluster_propagated`, `budget_exceeded`, `error`.

Исправить кэш LLM: сохранять reason/sensitivity и при cache hit заполнять
`PromptVersion` вердикта (`internal/scanengine/engine.go:880-910`). Добавить
фильтры и переход от колонки к её вызовам в UI/API.

По умолчанию сохранить экономичный каскад. Отдельный режим «LLM для каждой
колонки», если он нужен, должен быть явной опцией с предупреждением о стоимости:
сейчас LLM намеренно пропускается при уверенном решении слоёв 0–1, кластерном
распространении и small sample.

Приёмка: различимость ответа LLM и итогового вердикта, эквивалентное evidence
при cache hit/miss, корректные статусы пропусков, маскированные данные только,
API/UI/RBAC и migration-тесты.

## 4. S9-3 — пользовательский промпт на каждый скан

Сейчас UI/API принимают только source/profile, а system-промпт статический
(`internal/api/handlers_scans.go:106-130`, `internal/agentproxy/proxy.go:157-185`).

Реализовать:

- textarea дополнительной инструкции при запуске скана;
- единый `ScanOptions` вместо разрастания позиционных аргументов;
- передачу настройки через UI/API/CLI/scheduler → runner → scanengine →
  agentproxy;
- per-scan включение LLM вместо зависимости только от глобального `serve -llm`;
- неизменяемый snapshot эффективного промпта на весь прогон;
- сохранение исходного пользовательского текста, prompt hash и версии базового
  промпта в `scans`;
- включение prompt hash в ключ кэша: текущий ключ зависит только от глобальной
  `prompts.Version` (`internal/scanengine/engine.go:1122-1129`);
- лимиты длины промпта и HTTP body, строгий разбор JSON;
- аудит actor/hash/length без обязательной записи полного текста;
- явное правило для scheduled-сканов: сохранённый default источника либо всегда
  стандартный промпт.

Пользовательская инструкция добавляется к защищённому базовому system-промпту,
а не заменяет taxonomy enum, JSON-схему и анти-инъекционные правила.

Приёмка: разные промпты не разделяют кэш, действующий скан не меняется после
hot-reload, resume проверяет prompt hash, повторный прогон воспроизводим,
небезопасный/слишком большой ввод отклоняется, есть API/UI/CLI/scheduler-тесты.

## 5. S9-4 — отдельный агентский прогон описания БД

Сейчас Agent Proxy поддерживает только Classify/Verify; отдельного runner,
модели результата, endpoint и UI описания нет.

Реализовать `DescriptionRunner`:

- запуск по неизменяемому `scan_id`, без повторного подключения и сэмплирования
  исходной БД;
- запуск только для терминального скана; для partial — явная пометка неполного
  снимка;
- собственный versioned prompt и строгая JSON-схема ответа;
- статусы `running|done|failed|interrupted`, отмена и повторная генерация;
- история описаний, actor, agent/model, prompt version/hash, usage/cost,
  timestamps и ошибка;
- учёт в экономике и аудите, retention вместе со сканом;
- ограничение входных байтов и детерминированную агрегацию/разбиение больших БД;
- escaped-вывод ответа в UI и защиту от prompt injection через имена и reason.

Предлагаемый результат: назначение БД, группы таблиц, обнаруженные категории
данных, зоны PII/PCI/PHI, риски, неоднозначности и рекомендации по ревью.

Предлагаемые endpoint'ы:

- `POST /api/v1/scans/{id}/description-runs`;
- `GET /api/v1/description-runs/{id}`;
- `GET /api/v1/scans/{id}/description-runs`.

Для первой версии предпочтительны агрегированные вердикты без сырых значений.
Если для качества нужны имена таблиц/колонок, сначала изменить ADR изоляции и
определить допустимый контур (например, только локальный LLM).

Приёмка: повторный запуск не обращается к источнику, большой ввод ограничен,
partial маркируется, расходы учитываются, XSS/prompt injection не проходят,
RBAC/audit/retention/race и migration up/open/smoke зелёные.

## 6. S9-5 — выбор СУБД и новые коннекторы

Выбор ClickHouse/MongoDB уже есть в `/sources`
(`internal/web/templates/sources.html:19-24,46-49`), но список и валидация
зашиты вручную (`internal/config/sourceedit.go:207-234`).

Сделать:

- список типов из `connector.Types()` вместо HTML-дублирования;
- capability-метаданные коннектора и поля формы по выбранному типу;
- единую проверку type/DSN/URI/ref без расхождения UI и runtime;
- отображение поддерживаемых режимов сэмплирования и ограничений.

Порядок новых драйверов: PostgreSQL → MySQL/MariaDB → MS SQL. Oracle оценивать
отдельно из-за драйвера и требования pure-Go/cross-build.

Каждый новый коннектор включает `internal/connector/<db>/`, регистрацию,
потоковый Sample, schema/list/count/ping, классификацию ошибок/retry,
conftest, пример конфигурации и живой smoke. Миграция Verdict Store для самого
нового типа источника не требуется.

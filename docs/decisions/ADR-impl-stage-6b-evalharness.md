# ADR-impl: инкремент 6б — eval-harness

## D1. Каскад harness'а дублирует scanengine.verdict, а не импортирует его

**Выбор:** `internal/evalharness.Run` реализует порядок слоёв заново
(meta по имени → rules → `ensemble.Decide` → при Escalate LLM-классификатор
→ пересборка → верификатор `ApplyVerifier`; small_sample → UNKNOWN/pending),
не переиспользуя `scanengine.Engine`.

**Контекст:** движок привязан к store (вердикты, кэш, agent_calls, audit,
model_prices), коннектору и budget-стопу; его вердикт-функция приватна и
не выделяется без переработки S1–S5 (вне скоупа инкремента).

**Обоснование:** контур этапа 6 по ADR-impl-6а D1 самостоятелен: прогоны
должны быть дешёвыми и детерминированными. Дублирование — ~60 строк
порядка вызовов, при этом критичные правила (голосование, пороги, tie-break,
правило 4) живут в общем пакете `ensemble` и не дублируются; recognizer'ы —
общие `rules.Default()`. Риск дивергенции логики каскада при правках
движка принят и митигирован: self-check S6а связывает датасет с rules,
а изменения ensemble правил отразятся на обоих контурах одновременно
(тесты ensemble). При появлении третьего потребителя каскад выделяется
в общий пакет — отдельным ADR.

## D2. Sweep tau_accept — только по кандидатам слоёв 0–1, без LLM

**Выбор:** sweep переоценивает `ensemble.Decide` по закэшированным
кандидатам meta+rules каждой колонки; LLM-вызовы в перебор не входят.
LLM-режим отчитывается на одном конфигурированном tau.

**Отклонённая альтернатива:** sweep с LLM (перевызовы при каждом tau) —
дорого, недетерминированно (ответы модели плавают) и зависит от стенда.

**Обоснование:** без LLM лейбл ансамбля инвариантен к tau (правила 3–5
все возвращают лучшего кандидата; меняется лишь ReviewStatus), поэтому
содержательный смысл sweep — trade-off «доля автопринятых ↔ F1 на
решённых»: строки таблицы несут F1_all, F1_decided, macro F1, счётчики
auto_accepted/pending. Это ровно тот рычаг, которым настраивается
п. 5.6 (tau_accept/tau_review) под SLA ревью.

## D3. Метрики по truth-лейблу; spoof-precision — отдельной строкой

**Выбор:** per-label P/R/F1 строятся по `Column.Label` (спуфы участвуют
как UNKNOWN — их `Spoofs` в метрики не подменяется, ADR-impl-6а D2);
отдельный блок `spoofs` считает долю спуфов, отнесённых к имитируемому
лейблу (ложные срабатывания чексумм/словарей).

**Обоснование:** выполняет букву контракта ADR-impl-6а D2; F1 по лейблу
не завышается ложными позитивами, а качество отбраковки спуфов видно
по spoof-precision (в baseline: CARD_NUMBER 0.000 — имена спуфов бьют
в слой 0; BANK_ACCOUNT 1.000).

## D4. Прайс $ — флаги, не store

**Выбор:** стоимость вызовов считается по флагам `-price-in/-price-out`
($/1M токенов), нули — учёт без цены (`prices_set: false`).

**Контекст:** blueprint п. 11.1 хранит `model_prices` в SQLite store;
в контур harness'а store не входит (D1).

**Обоснование:** честный внешний вход без подтягивания SQLite ради одного
прайс-листа; формула та же, что у движка (`callCost`, округление 6 знаков,
накапливаемая сумма округляется на каждом шаге). Нормировка «на 1000
колонок» — буква п. 16.6.

## D5. Отчёт без wall-clock, закоммичен в репозитории

**Выбор:** `evals/reports/report.json` не содержит меток времени
генерации; схема версионируется semver (`schema: 1.0.0`).

**Обоснование:** воспроизводимость как требование формата (симметрично
ADR-impl-6а D3): два прогона побайтово идентичны (проверено cmp), diff
отчёта показывает только реальное изменение качества (правка
recognizer'ов, таксономии, tau). Длительность прогона — в консоли, не в
артефакте.

# ADR-impl: инкремент 6в — метрики и наблюдаемость

Дата: 2026-10-22
Статус: accepted
Связь: blueprint п. 17 (метрики, алертинг), п. 14.2 (аудит), п. 10.1
(LLM-изоляция), R9 (backlog ревью); прогресс —
`docs/progress/2026-10-22-stage-6v-observe.md`

## D1. Два слоя метрик: Meter (процесс) + Snapshot (store)

**Выбор:** процессные счётчики — атомарный `observe.Meter` (пишет
scanengine, живёт до перезапуска, expvar `zond/process`); бизнес/
технические агрегаты — `observe.BuildSnapshot` поверх store за окном
(24ч, expvar `zond/store`, API, дашборд /cost).

**Отклонённая альтернатива:** единый in-memory реестр — теряет историю
при перезапуске; только store-агрегаты — не покрывает latency/счётчики
текущего прогона в реальном времени.

**Обоснование:** разные времена жизни и читатели. Токены/$ и доля без
LLM историчны (п. 17, сверка со счётом провайдера) → store; счётчики
«сколько сейчас» → процесс. Оба слоя сходятся в одном `/debug/vars`.

## D2. Перцентили latency — в Go, store отдаёт выборку

**Выбор:** `LLMWindowStats` возвращает отсортированную выборку
`latency_ms` ok-вызовов окна; p50/p95 считает observe ближайшим рангом.

**Обоснование:** SQLite без оконных percentile-функций; выборка за сутки
— тысячи значений, сортировка в Go тривиальна и тестируема; SQL остаётся
простым. Токены/$ — только ok-вызовы (конвенция движка: cache_hit не
тратит токенов, error не засчитывается в экономику прогона).

## D3. Алерты — таблица с дедупом открытых, а не поток событий

**Выбор:** миграция 0007 `alerts` (rule, severity, target, message,
state open/resolved, last_seen_at); открытый (rule,target) не дублируется
(INSERT … WHERE NOT EXISTS, продление last_seen); угасание правила
закрывает алерт следующим проходом; события raise/resolve дублируются в
audit (CatAlert, actor scheduler) и webhook.

**Отклонённая альтернатива:** алерты как чистые audit-события (без
таблицы) — нет состояния «открыт/закрыт», невозможен дедуп и список
«что сейчас горит» без вычислений над логом.

**Обоснование:** оператору нужен актуальный набор проблем (как runbook-
подход), история сохраняется; дедуп на уровне SQL устойчив к расписанию
(каждые 5 мин) и не плодит строки.

## D4. Webhook — отдельный исходящий HTTP-клиент в observe; depguard
## осознанно расширен

**Выбор:** доставка событий raised/resolved через `observe.Webhook`
(net/http), URL из ENV `ZOND_ALERT_WEBHOOK`; исключение internal/observe
добавлено в depguard-правило llm-only-via-agentproxy с комментарием.

**Обоснование:** прецедент пакетов api/auth/web (HTTP без вызова LLM):
изолирующим для п. 10.1 является agentproxy, а не запрет импорта. Webhook
не трогает LLM-контур; fail-closed (таймаут 5с, без ретраев, ошибки в
лог). URL из ENV — п. 12 (секреты/env, не конфиг); интеграции
Slack/Telegram вне скоупа (п. 20).

## D5. Правило backup_failed — отложено до этапа 7

**Выбор:** в S6в реализованы budget_exceeded, pending_backlog (R9),
llm_unavailable, audit_chain_break; backup_failed не реализовано.

**Обоснование:** алерт без источника событий (бэкапа нет) — dead code;
закроется инкрементом backup (п. 15.2) этапа 7 одним правилом поверх
появившихся записей.

# ADR-impl: инкремент 5а — аудит-канал (audit_log, hash-chain, verify/export)

Дата: 2026-10-19
Статус: accepted
Связь: blueprint п. 14.2 (ADR-0013), п. 11.1, п. 13; runbook
`docs/runbooks/audit-hash-chain-broken.md`

## D1. Аудит пишется транзакциями домена, а не отдельным писателем

**Выбор:** `audit.AppendTx(ctx, tx, events)` вставляет события внутри той же
транзакции store, что вердикты и agent_calls. События жизненного цикла
(scan_start/finish) — отдельной транзакцией через `store.AppendAudit`.
Порядок цепочки гарантирован `SetMaxOpenConns(1)` и последовательностью
дижка (single-instance, ADR-0014).

**Отклонённая альтернатива:** отдельный `Auditor` со своим соединением и
mutex (по architecture.md п. 6 «audit writer: 1 goroutine, mutex»). При
попытке реализации выяснилось: второе соединение к SQLite + цепочка через
неё даёт гонку порядка с доменными транзакциями, а атомарность
«действие+аудит» (п. 13/14.2) без общей транзакции не достигается. Очередь
писателя остаётся правильным решением для serve-режима с конкурентными
HTTP-сканами; при появлении `serve` (инкремент 5г) writer-очередь введём
поверх этих же примитивов.

**Следствие:** если HTTP-сканы появятся раньше writer-очереди — блокировка;
контролируется порядком инкрементов.

## D2. Genesis prev_hash = "" (пустая строка)

Фиксируем начало цепочки: первая запись ссылается на prev_hash "".
Детерминировано, просто для verify, не требует секрета. Любое изменение —
только с версией формата и миграционной стратегией (runbook, п. 8).

## D3. Каноническая форма записи

`canonical = json.Marshal(map[string]any{seq,ts,actor,category,action,target,
details_json}) + "\n"`, ключи сортирует stdlib (encoding/json для map — ключи
в лексикографическом порядке). Детерминизм подтверждён тестом
(`TestCanonicalDeterministic`): одинаковое событие в двух журналах даёт
одинаковый hash. Изменение формата = разрыв всех исторических цепочек —
запрещено без версии и адаптера верификации (зафиксировано в runbook).

## D4. Fail-closed на ошибках аудита

scan_start без аудит-записи отменяет скан; export без аудит-записи не выдаёт
данные; FK-провал доменной записи откатывает её аудит. На уже падающем пути
(list tables) scan_finish — best effort (скан уже несостоявшийся).
Обоснование: п. 14.2 «все действия журналируются» — действие без записи
обязано падать, иначе аудит деградирует до best-effort.

## D5. Фильтр scan_id через details_json LIKE

События вызовов агентов имеют target `agent:<id>`; связь со сканом —
`details.scan_id`. Фильтр `/audit`/export по scan_id матчит target и
подстроку `"scan_id":"<id>"` в details. Отклонена альтернатива «отдельная
колонка scan_id» — схема п. 11.1 фиксирована blueprint'ом; LIKE по JSON
приемлем для объёмов MVP. При росте журнала — предложение изменения в
blueprint (миграция + колонка), не частная правка.

## D6. Не вошло и почему (фиксация границ инкремента)

- SIEM-sink с очередью повторов — требует долгоживущего процесса; появится
  с `serve`/scheduler (5г). До тех пор «потеря недопустима» = транзакции
  локального журнала.
- Retention-очистка — только scheduler'ом (п. 15.4), не CLI-хаком.
- События auth/review/config/secrets/admin — без SSO/API/hot-reload писать
  нечего; категории и формат Actor зарезервированы.

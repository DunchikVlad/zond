# ADR-security: изоляция LLM — Agent Proxy как единственная точка вызова

Статус: accepted
Дата: 2026-10-18
Основание: blueprint п. 10.1 (изоляция), п. 5.3 (контракт агента), п. 16.3 (изоляционные
тесты), п. 14 (безопасность)
Контекст: этап 4 (ядро) — LLM-слой
(`docs/progress/2026-10-18-stage-4-llm-core.md`)

## Контекст

LLM-вызов — главный канал потенциальной утечки ПИИ из системы (наружу, на внешний
эндпоинт). Blueprint требует: ни одно значение не покидает контур без маскирования,
ни один пакет не вызывает LLM напрямую, тело запроса не содержит идентификаторов
инфраструктуры (БД/таблиц/хостов/путей).

## Решение

Изоляция реализуется **тремя независимыми уровнями** (defense in depth):

1. **Единственная точка вызова** — `internal/agentproxy`. Только он формирует и
   отправляет HTTP-запрос к LLM. Контролируется **статически**: depguard-правило
   `llm-only-via-agentproxy` запрещает импорт `net/http` любым пакетом вне
   `internal/agentproxy` (проверка в CI на каждый PR).
2. **Маскирование до proxy** — `internal/agentproxy/mask`. Значения короче 5
   символов исключаются из пула (re-identification риск); остальные маскируются
   по профилю (PAN 6+4, телефон код+2, email local→`a***`, IP октет, ИНН/счёт 1+1).
   Версия профиля войдёт в ключ кэша (4б).
3. **Контрактный авто-тест (п. 16.3)** — fake-LLM (httptest) записывает тело;
   тест проверяет отсутствие в нём сырых PAN/телефонов/ИНН/email, имён
   БД/таблиц/хостов/путей, и что конверт содержит только `model`+`messages`.
   Независимость вызовов (system+user, нет сквозного контекста) — отдельным тестом.

Дополнительно:
- **Конверт минимален** (п. 5.3): только `column_native_type`, `values`,
  `taxonomy_version` — никаких идентификаторов инфраструктуры по построению.
- **Анти-инъекция в промпте**: system инструктирует игнорировать команды внутри
  `<values>`; значения — в явных разделителях (prompts.Version = "1").
- **Строгая валидация ответа**: label из таксономии, confidence [0,1], sensitivity
  enum, reason_ru [1,300]; невалидный — ретрай (п. 6), не принимается в вердикт.

## Альтернативы (отклонены)

- **Маскирование на уровне sampler/scanengine**: размывает ответственность; маск
  должен быть неотделим от точки вызова, чтобы ни один путь к LLM не обошёл его.
- **Только статический контроль (depguard)**: не проверяет содержимое тела;
  необходим runtime-авто-тест п. 16.3.
- **Только runtime-авто-тест**: не мешает будущему коду добавить прямой HTTP-вызов
  мимо proxy; нужен и статический барьер.
- **Передача сырых значений с инструкцией LLM «не запоминать»**: прямой нарушение
  п. 10.2 и privacy-by-design (п. 18.2); маскирование обязательно до вызова.

## Последствия

- Утечка ПИИ через LLM-канал блокируется на трёх уровнях: статика (нет прямых
  вызовов), маскирование (нет сырых значений), контракт (нет идентификаторов).
- Любой новый код, вызывающий LLM мимо proxy, ломает CI (depguard) — изоляция
  самосподдерживающаяся.
- Egress-политика (allowlist, offline, п. 10.7) — следующий инкремент (4в);
  сейчас endpoint ограничен только конфигом, не сетевым барьером прокси.
- Маскировщик эвристический: FREE_TEXT без совпадений слоя 1 уходит усечённым,
  но не placeholder-маскированным — placeholder'ы для FREE_TEXT подключаются в 4в.

## Дополнение S9-3 (2026-10-26): пользовательская инструкция на скан

Контекст: запуск прогона (UI/API/CLI) получил опциональную инструкцию
оператора — контекст предметной области, добавляемую в system-промпт
классификатора и верификатора (`prompts.SystemWithInstruction`,
блок `<operator_instruction>`).

Решение: дополнение не ослабляет изоляцию, а расширяет доверенный контур:

1. **Инструкция — доверенный ввод, не данные БД.** Канал защищён RBAC
   (действие `scan`, admin/токен со scope `scan`), поэтому она подставляется
   в system-промпт напрямую. Конверт (user) по-прежнему содержит только
   `column_native_type`, `values`, `taxonomy_version` — идентификаторы
   инфраструктуры не передаются (п. 5.3), авто-тест изоляции п. 16.3
   расширен и проверяет это для вызовов с инструкцией.
2. **Неотменяемость защищённой части.** Блок инструкции добавляется ПОСЛЕ
   enum лейблов, схемы ответа и анти-инъекционных правил и текстуально
   фиксирует, что эти правила остаются в силе. Изменение структуры промпта
   по-прежнему требует новой `prompt_version` (bump до "2" в S9-3).
3. **Лимиты и fail-closed на границе.** ≤2000 символов, запрет NUL,
   нормализация trim в `prompts.NormalizeUser`; UI, REST (включая лимит тела
   1 МБ и строгий разбор JSON) и CLI отклоняют невалидный ввод до runner.
4. **Прозрачность и воспроизводимость.** Хэш инструкции входит в ключ кэша
   вердиктов (разные инструкции не делят кэш); версия базового промпта, хэш
   и исходный текст сохраняются в `scans`; аудит старта фиксирует
   actor/hash/длину без полного текста; resume сверяет оба значения
   fail-closed и воспроизводит сохранённый промпт.

Scheduled-прогоны — всегда со стандартным (пустым) промптом и default-LLM:
фоновый канал не принимает пользовательский ввод.

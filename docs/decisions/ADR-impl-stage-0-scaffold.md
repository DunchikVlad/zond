# Решение: стартовать реализацию с минимального scaffold-этапа

Статус: accepted  
Дата: 2026-10-18  
Автор: Coordinator / Stage 0

## 1. Контекст
Проект `classifier` уже имеет сильную проектную документацию:
- `blueprint.md` как source of truth;
- `architecture.md` как модель реализации.

Перед началом feature-разработки требуется безопасно перейти от проектной спецификации к исполнимой кодовой базе.

Связь с исходными документами:
- `blueprint.md`:
  - п. 4 — структура репозитория
  - п. 5 — контракты как код
  - п. 16 — тестирование и eval
  - п. 21 — этап 0
  - п. 22 — DoD
- `architecture.md`:
  - п. 3 — компонентная структура
  - п. 7 — карта пакетов
  - п. 12 — анти-архитектура
  - п. 13 — traceability

## 2. Проблема
Нужно определить, как именно начинать разработку:
- сразу делать полноценный вертикальный feature slice,
- сначала построить инфраструктурный каркас,
- либо комбинировать оба подхода.

## 3. Рассмотренные варианты
### Вариант 1 — сразу делать feature slice без scaffold
Описание:
- сразу реализовать ClickHouse → sample → rules → verdict.

Плюсы:
- быстрый переход к видимой бизнес-ценности;
- ранняя проверка архитектуры на реальном сценарии.

Минусы:
- высокий риск хаотично принять стартовые контракты;
- возрастает вероятность архитектурных компромиссов на скорую руку;
- документационная и операционная база может отстать.

### Вариант 2 — сначала полный инфраструктурный фундамент
Описание:
- сначала сделать почти все каркасные подсистемы, CI, configs, logging, docs, skeleton packages.

Плюсы:
- структурированное начало;
- меньше импровизации в пакетах.

Минусы:
- слишком долго до первого проверяемого результата;
- высокий риск «framework before product»;
- можно переусложнить раннюю фазу.

### Вариант 3 — минимальный scaffold + затем вертикальный срез
Описание:
- на этапе 0 сделать только минимальный каркас,
- после этого перейти к узкому вертикальному срезу на этапе 1.

Плюсы:
- даёт рабочую базу без чрезмерного разрастания;
- сохраняет быстрый путь к первой бизнес-проверке;
- согласуется с blueprint и traceability этапов.

Минусы:
- требует дисциплины, чтобы scaffold не разросся;
- нужно чётко ограничивать, что не входит в этап 0.

## 4. Принятое решение
Выбран **вариант 3**:
- сначала минимальный scaffold;
- затем вертикальный срез как первый реальный feature path.

## 5. Почему выбрано именно это
Причины:
- соответствует `blueprint.md` этапу 0;
- снижает риск раннего архитектурного дрейфа;
- позволяет быстро перейти к проверяемому vertical slice;
- лучше подходит для multi-agent режима, где важно заранее определить write scopes и documentation discipline.

## 6. Последствия
Положительные:
- проще координировать несколько агентов;
- легче поддерживать package boundaries;
- можно заранее внедрить шаблоны документации и валидации.

Отрицательные / ограничения:
- нужно жёстко следить, чтобы scaffold не превратился в полуготовую платформу без полезного результата;
- часть интерфейсов может уточниться на этапе 1.

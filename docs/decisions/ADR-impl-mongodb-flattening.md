# ADR-impl: MongoDB — флаттенинг в dot-path и схема по сэмплу

Статус: accepted
Дата: 2026-10-18
Основание: blueprint п. 8 (специфика MongoDB), п. 16.2 (conftest), п. 5.1 (SPI)
Контекст: этап 2 — MongoDB-коннектор + контрактные тесты
(`docs/progress/2026-10-18-stage-2-mongodb-conftest.md`)

## Контекст

MongoDB — schemaless: у коллекции нет фиксированной схемы, документы вложенные,
поля полиморфны. SPI коннектора (п. 5.1) опирается на плоский список колонок с
нативными типами. Нужно решить, как отображать BSON-документы на плоские
колонки так, чтобы результат был сопоставим с реляционным CH (conftest п. 16.2)
и детерминирован для каскада 0→1.

## Решение

1. **Флаттенинг в dot-path** (п. 8): вложенный документ → `address.city`;
   массив скаляров → одна логическая колонка `tags[]` (до K=5 элементов на
   документ, общий пул сэмпла); массив документов → рекурсия `items[].field`,
   глубина ≤ 5, дальше — терминатор `...`.
2. **Флаттенер — чистая функция над `map[string]any`** (`flatten.go`),
   отделённая от драйвера: и GetSchema, и Sample используют одну реализацию,
   исключая расхождение dot-path. Покрывается unit/fuzz без Mongo.
3. **Схема — объединение ключей по сэмплу** (200 документов через `$sample`):
   тип пути — доминирующий BSON-класс; нестабильный (≥2 типов, каждый в >20%
   документов, где путь встретился) → `native_type "mixed"` + список типов.
4. **Типизация — по BSON-классу после приведения драйвером**: string/number/
   bool/null/object/array. objectId/uuid → строкоподобные; кандидат IDENTIFIER
   решается слоем meta со словарём имён (разделение ответственности).
5. **`_id` исключается** из классификации (`skipPath`, п. 8).
6. **`readPreference secondaryPreferred`** и `estimatedDocumentCount` для
   percent-сэмпла (п. 8, п. 13.2): чтения не бьют по primary, подсчёт — по
   метаданным.
7. **conftest.Harness**: общий контрактный набор + пер-БД фикстура/ожидания;
   обе БД подставляют совместимую фикстуру (строковая + nullable колонка).

## Альтернативы (отклонены)

- **Отдельная колонка на каждый индекс массива** (`tags.0`, `tags.1`, …):
  взрыв числа колонок, разные схемы у документов с разной длиной массива;
  противоречит «одна логическая колонка tags[]» п. 8.
- **Вывод схемы из $jsonSchema валидатора коллекции**: валидатор необязателен
  и часто отсутствует; не покрывает полиморфные коллекции. Сэмпл — честнее.
- **Точный `countDocuments` для percent-сэмпла**: дорого на больших коллекциях;
  `estimatedDocumentCount` (метаданные) достаточен для пропорции (п. 8, п. 13.2).
- **Классификация objectId/uuid → IDENTIFIER в коннекторе**: коннектор не
  владеет словарём имён и таксономией; его задача — нативный тип, лейбл —
  наверху каскада.

## Последствия

- Сопоставимая с CH модель плоских колонок: общий conftest прогоняется против
  обеих БД (п. 16.2).
- Массивы/вложенность урезаны (K=5, глубина ≤5): глубокие/широкие структуры
  сворачиваются в `...` → пометка FREE_TEXT + pending на уровне вердикта
  (эскалация — после этапа 4, LLM).
- Схема по сэмплу может не включать редкие поля (отсутствующие в 200 документах)
  — принятое ограничение MVP (п. 8: «схема = объединение ключей по сэмплу»).
- Новая зависимость mongo-driver/v2 — закреплена в go.mod (v2.9.2); риск
  первого живого прогона mitigируется CI.

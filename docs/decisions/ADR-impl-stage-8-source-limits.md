# ADR-impl: инкремент 8-2 — per-source лимиты и окна сканирования (п. 13.2)

Дата: 2026-10-24
Статус: accepted
Связь: blueprint п. 13.2 (лимиты источника, окна), п. 13 (чекпоинт — таблица),
п. 14.2 (аудит), п. 10.4 (budget-стоп); продолжение
`ADR-impl-stage-8-resource-governance.md` (S8-1); прогресс —
`docs/progress/2026-10-24-stage-8-2-source-limits-windows.md`

## D1. Лимиты — поля записи источника в connections.yaml, дефолты спецификации

**Выбор:** `max_concurrent_scans`/`max_concurrent_tables`/`query_timeout_s`/
`scan_window` — в `Source` (строгая схема, ADR-0009); `0`/опущено → дефолт
спецификации (1 / 2 / 300 с), отрицательные отклоняются при загрузке.

**Отклонённая альтернатива:** глобальные лимиты в detectors.yaml.

**Обоснование:** blueprint прямо: «лимиты на источник (в записи sources
connections.yaml)». Per-source — продуктивные и тестовые источники имеют
разную цену нагрузки. Дефолты — константы спецификации (прецедент D3 S8-1:
числа п. 13.2 фиксированы, не конфигурируемы произвольно).

## D2. Параллелизм — по таблицам, не по колонкам

**Выбор:** `max_concurrent_tables` — пул воркеров, каждый ведёт таблицу
целиком (схема → сэмплы колонок последовательно → коммит); слот семафором
`TableGate` на всю таблицу.

**Отклонённая альтернатива:** параллельные колонки внутри таблицы.

**Обоснование:** чекпоинт п. 13 — таблица (атомарный коммит вердикты+вызовы+
аудит); соединение драйвера одно на прогон — делить его между колонками
значит распараллелить внутренности без выигрыша лимита на источник
(семафор всё равно на таблицу). Предел нагрузки спецификации — «таблиц в
обработке одновременно».

## D3. Детерминизм breaker-серии: результаты применяются в порядке ListTables

**Выбор:** воркеры шлют результаты в канал; оркестратор применяет их
строго в порядке списка таблиц (буфер out-of-order). Серия «5 подряд
overload» и момент обрыва идентичны последовательному пути.

**Отклонённые альтернативы:** атомарный счётчик подряд по факту завершения
(недетерминировано — зависит от планировщика); полный отказ от параллелизма
при включённом breaker'е (теряется смысл лимита).

**Обоснование:** семантика S8-1 («5 подряд failed по source_overload»)
определена на порядке обхода таблиц; её нельзя делать функцией таймингов.
Цена — до `MaxTables` результатов в буфере; при сработке breaker'а подача
прекращается, начатые таблицы коммитятся (п. 13), не начатые не тронуты
(resume догонит).

## D4. Потокобезопасность движка: мьютексы на общем, буферы — локальные

**Выбор:** кластерер (п. 7.6), счётчики экономики (п. 17), стоимость/бюджет
(п. 10.4), прайс-кэш — под мьютексами; вызовы/аудит-события таблицы —
локальный `tableState` воркера (бывшие поля Engine), коммит той же
транзакцией вердиктов (п. 13).

**Отклонённая альтернатива:** каналы/агрегатор вместо мьютексов — сложнее
без выигрыша: критические секции короткие (append/инкремент), LLM-вызовы
вне секций.

**Обоснование:** минимальная правка существующих путей: последовательный
режим (`MaxTables<=0`) исполняется тем же кодом без конкуренции — мьютексы
прозрачны, регрессия покрыта существующими тестами.

## D5. `max_concurrent_scans` — семафор в runner'е, отказ до подключения

**Выбор:** `map[source]chan struct{}` ёмкостью лимита в `engineRunner`;
неблокирующий захват в `Start` → 502 `source_unavailable` сверх лимита;
слот освобождается по завершении прогона (defer).

**Отклонённые альтернативы:** очередь ожидания слота (меняет контракт
POST /scans — немедленный ответ); блокировка до таймаута (занятый HTTP-
обработчик ради тормоза источника).

**Обоснование:** прецедент S8-1 (отказ breaker'а до подключения) и D6
ADR-impl-5б (source_unavailable); API остаётся «scan_id сразу или ошибка».
CLI без семафора: один прогон на процесс — лимит вырождается в 1.

## D6. Окно — только шедулер; формат HH:MM-HH:MM локального времени

**Выбор:** `scan_window` проверяется в `scheduler.rescan`: вне окна —
разовый таймер до `NextStart`, аудит `scheduler/scan_deferred`; по
срабатывании таймера окно проверяется заново (сдвиг часов). Ручные старты
(API/CLI) не ограничиваются. Валидация формата при загрузке конфига
(fail-fast). Окно через полночь поддерживается; `start == end` отклонено.

**Отклонённые альтернативы:** блокировать ручные старты вне окна (спека:
«откладывается шедулером» — ручной старт осознан, блокировка мешает
аварийному скану); cron-выражение вместо окна (дублирует `schedule`);
UTC (оператор мыслил локальным временем контура — как cron robfig).

**Обоснование:** буква спецификации + fail-closed на вводе (битый формат
не стартует инстанс) + безопасная деградация (рестарт снимает таймеры —
перескан повторится по расписанию).

## D7. Дедлайн запроса — обёртка ctx на каждый вызов коннектора

**Выбор:** `queryCtx`: `context.WithTimeout(ctx, query_timeout_s)` на
GetSchema/CountRows/Sample каждой колонки; родительский ctx — общий
дедлайн/отмена прогона.

**Обоснование:** «таймаут запроса к БД (default 5 мин)» — это про запрос,
не про таблицу: тяжёлый сэмпл ограничен, серия таких таймаутов
классифицируется overload (S8-1) и трипает breaker — составной смысл
п. 13.2. Дополнительный дедлайн на таблицу избыточен: таблица = сумма
запросов, каждый уже ограничен.

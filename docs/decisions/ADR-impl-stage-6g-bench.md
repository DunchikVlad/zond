## D1. bench — подкоманда `cmd/eval`, не `zond` и не отдельный бинарь

**Выбор:** `eval bench` рядом с `generate`/`run`; `make bench` =
`go run ./cmd/eval bench`.

**Отклонённые альтернативы:** подкоманда `zond bench` (расширила бы
эксплуатационный CLI инструментом разработки — в blueprint п. 15 его нет);
отдельный `cmd/bench` (дублирование wiring'а контурa этапа 6).

**Обоснование:** прецедент ADR-impl-6а D1 — cmd/eval объявлен
инструментарием этапа 6, изолированным от store/секретов/SSO; bench —
тот же контур (только rules + verdict, сети нет). Нагрузочный тест по
п. 16.8 — часть тестовой стратегии этапа 6 рядом с eval-harness (п. 16.6).

## D2. Собственный детерминированный генератор, не evalset

**Выбор:** `internal/benchlab` генерирует поток значений напрямую
(math/rand/v2 PCG, seed флагом): позитивы с валидными чексуммами по всем
11 recognizer'ам + гарантированные негативы.

**Отклонённая альтернатива:** переиспользовать `evalset.Generate`
(масштаб до 1M: 50k колонок × 20) — потянуло бы taxonomy, manifest,
spoof-логику и фиксированный rows=20 эталонного датасета, сделав микс
неконтролируемым.

**Обоснование:** у артефактов разные цели: evalset — эталон для F1/$
(реалистичность распределения колонок), bench — измерение скорости
recognizer'ов (контроль профиля: доля позитивов, валидность чексумм,
отсутствие ложных матчей). Контроль выражен инвариантами тестами,
а не свойствами чужого генератора.

## D3. Формулы чексумм продублированы, не экспортированы из rules

**Выбор:** benchlab содержит свои компактные реализации (веса ФНС,
Лун, mod-97) рядом с генераторами.

**Отклонённая альтернатива:** экспортировать расчёты из
internal/analyze/rules — сделало бы их публичным API доменного пакета
ради тестового инструмента.

**Обоснование:** граница пакета rules (п. 10.1, ADR-impl-rules-
checksum-policy) важнее локального дубля; рассинхрон дублей с rules
ловится инвариантом TestPositiveCoverage («100% сгенерированных
позитивов матчится своим recognizer'ом») — в этом инкременте тест поймал
два реальных дефекта формул (Лун, 12-значный ИНН).

## D4. Отчёт bench — с wall-clock, в git не коммитится

**Выбор:** `evals/reports/bench.json` содержит duration/throughput
(недетерминированы), генерируется прогоном, в .gitignore; метрика —
stdout (`make bench`, лог CI-шага).

**Обоснование:** ADR-impl-6б требует детерминизма для `report.json`
(повторный прогон — побайтовый JSON, baseline качества в git). Bench —
не baseline, а измерение; фиксировать недетерминированный файл в git —
гарантированный diff-шум. Конфликта решений нет: разные артефакты,
разные правила.

## D5. CI-гейт — floor по NFR, без upper-bound

**Выбор:** шаг ci.yml падает (exit 1) только если throughput < 100 000
значений/мин на ядро; регрессия вверх — не блокируется.

**Обоснование:** п. 16.8 требует «проверка NFR п. 18 … прогон в CI на
каждый PR» — это floor-гарантия. Факт на эталонной машине ~101M знач/мин
(запас ~×1000) — медленные раннеры не ломают гейт; деградация recognizer'ов
в десятки раз будет поймана. Верхний порог относился бы к конкретной
машине и давал бы ложные падения.

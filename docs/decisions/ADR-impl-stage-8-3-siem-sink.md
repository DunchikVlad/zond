# ADR-impl: инкремент 8-3 — SIEM-sink аудит-журнала (п. 14.2)

Дата: 2026-10-24
Статус: accepted
Связь: blueprint п. 14.2 (внешний sink, «потеря событий недопустима»),
ADR-0013 (два канала журналирования), ADR-0014 (single-instance),
п. 17 (backlog в наблюдаемости); прогресс —
`docs/progress/2026-10-24-stage-8-3-siem-sink.md`

## D1. Очередь = сам журнал; закладка, а не per-event очередь с dual-write

**Выбор:** воркер читает `audit_log` за закладкой `audit_sink_state.last_seq`
(миграция 0009, одна строка на инстанс) и двигает её только за
подтверждённо доставленное событие. Записи при вставке не помечаются.

**Отклонённая альтернатива (первая редакция S8-3):** per-event таблица
`audit_sink_queue` + пометка seq при коммите аудита (dual-write через
`AppendTx(withSink)`).

**Обоснование:** dual-write можно обойти: аудит пишется не только через
`store.AppendAudit`, но и внутри транзакций (`SaveVerdictsWithCalls` —
вызовы агента, токены, ревью) общим `audit.AppendTx`. Чтобы не пропустить
событие, пометку пришлось бы протаскивать во все пути записи — хрупко и
нарушает «потеря недопустима» на первом же пропущенном пути. Закладка по
самому журналу не зависит от пути записи: журнал append-only (миграция
0004), порядок = seq, закладка в той же БД переживает рестарт. Минус —
повторная доставка при сбое «записано, но закладка не сдвинулась» —
принимаем (ат-least-once, D4).

## D2. Порядок доставки — строго по цепочке (seq)

**Выбор:** воркер читает `WHERE seq > last ORDER BY seq` и останавливается
на первой неудаче (закладка не двигается, `last_error` фиксируется).

**Отклонённая альтернатива:** независимые повторы на событие (per-event
next_retry) — нарушает порядок: SIEM получает события не в порядке
цепочки, сверка hash-chain на стороне SIEM ломается (prev_hash идёт по
порядку). Порядок — часть контракта сверки (п. 14.2, hash-chain).

## D3. На проводе — каноническая форма записи (CanonicalEntry)

**Выбор:** наружу уходит `canonical(entry)` (п. 14.2: UTF-8 JSON с
сортированными ключами + `\n`): NDJSON для json-tcp, CEF-строка с
канонической записью в `msg` для syslog. `CanonicalEntry` экспортирована
из пакета audit.

**Обоснование:** внешняя сверка hash-chain не зависит от внутреннего
представления (поля БД): SIEM получает ровно то, что подписано в
`entry_hash`. CEF — транспортный фрейминг, полезная нагрузка — та же
каноническая строка.

## D4. At-least-once: идемпотентность по seq — на приёмнике

**Выбор:** закладка двигается после записи в сокет; сбой между записью и
продвижением даёт повторную доставку последней записи после восстановления.

**Обоснование:** п. 14.2 требует «потеря недопустима», не exactly-once.
Гарантия «не потерять» достигается закладкой (запись не снимается до
подтверждения); дубликат последней записи при редком сбое — цена
отсутствия транзакции «сокет+БД». Приёмник дедуплицирует по `seq`
(присутствует в канонической форме и в CEF-заголовке).

## D5. Недоступный sink не роняет запись аудита

**Выбор:** sink — только читатель журнала и писатель закладки; на запись
аудита (п. 14.2 «все действия журналируются») он не влияет. Backoff между
циклами при ошибках журнала/закладки (30 с), при недоступности sink —
повтор на следующем тике (2 с), закладка не двигается.

**Обоснование:** fail-closed по журналу, не по sink (прецедент п. 14.2:
действие без аудита не совершено — но аудит локален и append-only; sink —
опция доставки). Иначе недоступный SIEM останавливал бы продукт —
недопустимая связанность для опциональной интеграции.

## D6. Пакет audit не тянет config

**Выбор:** зеркальный `audit.SinkConfig` (Kind/Address/Proto); конвертация
`config.SinkConfig` → `audit.SinkConfig` — в cmd (`auditSinkConfig`).

**Обоснование:** граница слоёв architecture.md п. 3: audit — доменный
пакет журнала, config — схема YAML. Audit уже оперирует `*sql.DB` напрямую
(Verify, List) — sink в том же стиле; `store.DB()` открывает инфраструктурный
доступ к соединению для чтения очереди (один писатель, SELECT+UPDATE
закладки).

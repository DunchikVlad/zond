# ADR-impl: инкремент 5б — REST API v1 (scans/verdicts/review/drift/export/stats)

Дата: 2026-10-19
Статус: accepted
Связь: blueprint п. 11.2 (REST API), п. 11.1 (схема), п. 13 (атомарность),
п. 14.1 (correlation id), п. 14.2 (аудит), ADR-0010 (маскирование),
ADR-impl-5а (аудит-канал), architecture.md п. 6 (процессная модель serve).

## D1. Аутентификации пока нет: actor = "api", listen — только loopback

Blueprint п. 11.2 требует аутентификацию всех мутаций и экспорта (SSO-сессия
или API-токен), но SSO — инкремент 5в. До неё сервер **по умолчанию слушает
только 127.0.0.1** (флаг `-addr`), а все действия аудируются с actor `api`
(формат `sso:<subject>`/`token:<id>` зарезервирован п. 14.2 и появится в 5в).
Вынос порта на внешний интерфейс до появления SSO — осознанное отклонение
от п. 11.2, зафиксированное в security-заметке инкремента; `zond serve`
предупреждает в usage, что `-addr` по умолчанию loopback именно поэтому.

**Следствие:** код 403/RBAC-матрица п. 11.3 не реализованы в 5б — приходит
с SSO (5в). Категории аудита auth/authorization зарезервированы (5а, D6).

## D2. Ревью атомарно: вердикт + review_events + аудит одной транзакцией

`store.ApplyReview` обновляет `review_status/final_label/reviewed_*` вердикта,
вставляет строку `review_events` и аудит-событие категории review в **одной
транзакции** (п. 13/14.2: действие без аудита не совершено). Конфликты
(повторное действие в тот же статус, relabel на тот же лейбл, relabel без
лейбла, неизвестное действие) откатываются ДО какой-либо записи — ни
review_events, ни аудита от отклонённых действий не остаётся (подтверждено
тестом `TestApplyReviewConflicts`).

**Отклонённая альтернатива:** сначала обновить вердикт, аудит «догнать»
отдельным вызовом — даёт окно, где действие совершено, а записи нет.

## D3. review_events — append-only триггерами, как audit_log

Миграция 0005 повторяет паттерн 0004: UPDATE/DELETE запрещены на уровне БД
(защита в глубину). История ревью — юридически значимый след (кто и когда
пере-классифицировал), не переписывается. ID события — crypto/rand hex(16),
как у agent_calls.

## D4. scan_id возвращается до завершения прогона: Engine.ScanWithID

POST /api/v1/scans обязан ответить `{scan_id}` сразу (п. 11.2), а
`engine.Scan` генерировал id внутри и блокировался до конца. Добавлен
`Engine.ScanWithID(ctx, conn, source, profile, scanID)` — прогон исполняется
с заранее выданным идентификатором; CLI `Scan` делегирует ему (поведение CLI
не изменилось). Runner serve'а валидирует источник/профиль/подключение
(`Ping`) ДО старта фонового прогона — клиент получает `source_unavailable`
(502) синхронно, а не «прогон умер в фоне».

## D5. Мягкая остановка: ctx-отмена между таблицами + финализация без ctx

Stop — отмена контекста прогона. Движок проверяет `ctx.Err()` в цикле
таблиц: прогон фиксируется `interrupted` с чекпоинтами обработанных таблиц.
Финализация (агрегаты, stats_json, аудит scan_finish) идёт через
`context.WithoutCancel` — иначе запись в store на отменённом ctx падает и
прогон остаётся «вечным» running. Без этого изменения отмена ctx превращала
каждую последующую таблицу в failed и давала ложный partial.

## D6. Один активный прогон на источник

Runner держит реестр `source → running`; повторный старт на занятом источнике
— `source_unavailable` (п. 13.2 per-source caps: 1 скан/источник). Полный
resource governance (table pool, окна) — scheduler этапа 5г; защита от
двойного скана одного источника нужна уже сейчас: hash-chain аудита
последователен (SetMaxOpenConns(1)), а конкурентные прогоны одного источника
не имеют смысла по постановке.

## D7. Конверт ошибок и код verdict_not_found

Единый конверт `{error:{code,message,details}}` — по п. 11.2. Коды blueprint:
`invalid_request, source_unavailable, scan_not_found, review_conflict,
internal`. Добавлен `verdict_not_found` (GET/POST по несуществующему
вердикту): использовать `scan_not_found` для вердикта семантически неверно,
а `invalid_request` скрывает 404. Расширение набора кодов — допустимое
развитие п. 11.2 (список не закрыт), зафиксировано здесь.

## D8. Дрейф: эффективный лейбл и порог шума confidence

Дрейф (п. 11.2 GET /drift) сравнивает два последних **не-running** прогона
источника: текущий — свежайший, базовый — предыдущий; `since` ограничивает
период снизу. Лейбл колонки — с учётом ручного ревью (`final_label`
приоритетнее автоматического, п. 5.4): ревьюерское пере-классифицирование —
тоже дрейф. Смена confidence учитывается от Δ≥0.05 — меньшие колебания это
шум сэмплирования, а не дрейф (п. 11.3 «смены лейблов/уверенности»).

## D9. Лимит экспорта — 409 с async-намёком; экспорт аудируется до выдачи

Сверх `export_max_rows` (флаг `-export-max-rows`, default 50 000) экспорт
отклоняется 409 с `details.async=true` (задел под фоновый экспорт п. 11.2 —
сама фоновая выгрузка по ссылке придёт со scheduler). Аудит-событие
`verdicts_export` пишется ДО передачи данных и только при успешной выдаче:
отказанный экспорт не маскируется под совершённый (fail-closed, п. 14.2).

## D10. depguard: net/http разрешён в internal/api и cmd

Правило `llm-only-via-agentproxy` с этапа 0 запрещало net/http вне
agentproxy «до этапа 5» (комментарий в .golangci.yml). Инкремент 5б —
первый HTTP-код вне proxy: исключения добавлены для `internal/api/**` и
`cmd/**`. Граница изоляции LLM не ослабла: изолирующим звеном остаётся
agentproxy (единственный импортёр LLM-вызовов), а api/cmd не обращаются к
LLM-эндпоинтам напрямую — проверяется код-ревью и отсутствием импорта
LLM-клиентов в api (тестовый httptest-сервер в `*_test.go` разрешён был
всегда).

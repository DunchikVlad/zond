# ADR-impl: checksum-recognizer'ы слоя 1 — самодостаточная сумма как критерий 0.99

Статус: accepted
Дата: 2026-10-18
Основание: blueprint п. 5.6 (семантика confidence), п. 16.1 (золотые вектора), п. 21 (этап 3)
Контекст: этап 3 — полный regex-слой
(`docs/progress/2026-10-18-stage-3-regex-layer.md`)

## Контекст

Blueprint п. 5.6 задаёт правило «checksum совпал → confidence 0.99 (конец
пайплайна)». Не все типы имеют контрольную сумму, а у некоторых сумма требует
внешних данных. Нужно формальное правило, какие recognizer'ы помечаются
`HasChecksum=true` и получают право на 0.99.

## Решение

`HasChecksum=true` выставляется **только если контрольная сумма вычисляется из
одного значения колонки без внешних данных**:

- **checksum** (`HasChecksum=true`): ИНН 10/12 (ФНС), Luhn/PAN, СНИЛС (mod 101),
  IBAN (ISO 13616 mod-97). Сумма самодостаточна → 0.99, конец каскада.
- **форматные** (`HasChecksum=false`): email, phone, паспорт, счёт РФ, IP, дата,
  UUID — только структурная/диапазонная валидация, confidence по доле матчей
  (0.90/0.70/0.50).

**Счёт РФ — особый случай**: контрольный ключ 9-го разряда вычисляется по БИК
(положение ЦБ, веса 7-1-3). БИК — отдельная колонка, поэтому одиночное значение
счёта не даёт самодостаточной суммы. Проверка вынесена в экспортируемую
`BankAccountKeyCheck(bik, account)` для будущего вызова кластерным слоем
(п. 7.6), когда БИК и счёт окажутся в одном кластере — тогда пара «БИК+счёт»
получит 0.99.

## Альтернативы (отклонены)

- **`HasChecksum=true` для счёта по частичной проверке** (структура + код валюты):
  это не контрольная сумма, а формат; дало бы ложные 0.99 на синтетике.
- **Regex для IP**: допускает 256.1.1.1 и подобное; строгий парсинг netip/net
  точнее и не сложнее.
- **Лейбл DATE_OF_BIRTH в date-recognizer**: дата рождения определяется диапазоном
  и контекстом (кластерный слой), не форматом; regex выдаёт DATE_TIME.
- **Ручное перечисление 50+ векторов на тип**: подвержено «ошибке в спецификации»
  и не масштабируется; детерминированная генерация по спецификации (ФНС/ЦБ/ISO)
  надёжнее, негатив — испорченный контрольный разряд.

## Последствия

- 0.99 дают только типы с надёжной самодостаточной суммой — ложных «концов
  пайплайна» на форматных совпадениях нет.
- Золотые вектора checksum-типов ≥50/50 генерируются детерминированно — риск
  «генератор и recognizer используют одни веса» (систематическая ошибка) снят
  только частично; окончательно закрывается портом внешнего эталона (R7).
- Кластерный слой (п. 7.6) получает готовую `BankAccountKeyCheck` для пары
  БИК+счёт; DATE_OF_BIRTH — для диапазона дат.

## 2. Что подтверждено тестами

- **Hash-chain** (`internal/audit`): три события в одной транзакции сходятся
  (`TestAppendAndVerifyChain`); детерминизм канонической формы — одинаковое
  событие в двух независимых журналах даёт одинаковый entry_hash
  (`TestCanonicalDeterministic`); genesis prev_hash = "" (`TestGenesisPrevHash`);
  пустой список событий — no-op.
- **Обнаружение подмены**: изменённый entry_hash → `Verify` указывает seq=1;
  forged prev_hash → разрыв на seq=2 (`TestVerifyDetectsBrokenChain`,
  `TestVerifyDetectsWrongPrevHash`).
- **Append-only триггеры** (store, миграция 0004): `UPDATE`/`DELETE` через
  прямой доступ к БД → ABORT; после попыток подмены цепочка цела
  (`TestAuditLogAppendOnlyTriggers`).
- **Атомарность с доменной транзакцией**: `SaveVerdictsWithCalls` с FK-провалом
  вызова откатывает и аудит-события — в audit_log 0 записей
  (`TestSaveVerdictsWithCallsRollsBackEvents`); цепочка продолжается через
  несколько пачек (`TestAppendAuditChainAcrossCalls`).
- **E2E движка** (`internal/scanengine`): скан с LLM (2 серые колонки,
  classify+verify) порождает ровно 6 событий — scan_start, scan_finish и 4
  `agent_call` с обязательными полями (call_id, scan_id, verdict_id, model,
  status, tokens, cost); актор `cli`; цепочка сходится
  (`TestScanWritesAuditEvents`). Скан без LLM — start+finish, порядок
  событий корректен (`TestScanWithoutLLMAudited`).

## 3. Не проверено / ограничения

- Внешний SIEM-sink и очередь повторов — не реализованы в инкременте (см.
  «Не вошло» прогресса); гарантия «потеря событий недопустима» пока
  распространяется только на локальный журнал (транзакционность).
- Нагрузка: последовательная запись через одно соединение не пропускалась
  через race/нагрузочный стенд — движок последователен по построению,
  race-прогон зелёный; узкое место появится в serve-режиме (тогда —
  writer-очередь п. 15.1).
- Retention-очистка не реализована: журнал растёт неограниченно до
  появления scheduler (п. 15.4) — для dev-контура приемлемо, для прода —
  обязательна до релиза v0.1 (DoD п. 22).
- Верификация на больших журналах — полный пересчёт O(n); до появления
  подписанных снапшотов (п. 14.2) это единственный метод.

## 4. Остаточные риски

- Триггеры защищают от UPDATE/DELETE, но не от DROP TABLE — компрометация
  с правами на схему БД вне скоупа приложения (шифрование тома/ACL — п. 14).
- `details_json LIKE` в фильтре scan_id — строковый поиск по JSON; при
  больших журналах заменить на выделенную колонку scan_id (несовместимо с
  п. 11.1 без миграции — зафиксировано, при росте обсудить в blueprint).

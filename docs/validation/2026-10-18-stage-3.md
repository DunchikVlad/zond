## 3. Подтверждено поведение по blueprint

- **п. 16.1 (≥50/50)**: checksum-типы ИНН/Luhn/СНИЛС покрыты объёмными векторами
  (по 55 валидных + 55 невалидных), детерминированной генерацией по спецификации;
  негатив — испорченный контрольный разряд.
- **п. 5.6 (checksum → 0.99)**: `HasChecksum=true` только у самодостаточных
  checksum (ИНН, Luhn, СНИЛС, IBAN); форматные (email, phone, паспорт, счёт, IP,
  дата, UUID) — confidence по доле матчей.
- **п. 5.5 (лейблы)**: IBAN/счёт → BANK_ACCOUNT; UUID → IDENTIFIER; IP →
  IP_ADDRESS; дата → DATE_TIME — тестом `TestLabels`/`TestDefaultStage3Complete`.
- **Контрольные суммы по спецификации**: ФНС (ИНН), СНИЛС (mod 101), ЦБ (ключ
  счёта, веса 7-1-3), ISO 13616 (IBAN mod-97), Лун (PAN) — генераторы согласованы
  с recognizer'ами авто-тестами.

## 4. Что не проверено (с причинами)

- **Порт RU-набора из angryscan-core (NOTICE, риск R7)** — независимая сверка
  весов ИНН/Luhn с эталонным набором не выполнялась; генератор и recognizer
  используют одни веса (защита от «ошибки в спецификации» — только портом).
- **Полнота векторов форматных типов** (email/phone/паспорт/счёт/IP/дата/UUID) —
  сейчас ~7–15 на тип; bulk ≥50/50 покрывает только checksum-типы (для форматных
  объём менее критичен — нет контрольной суммы, дающей 0.99).
- **F1 на эталонном датасете** (п. 22, ≥0.97 структурных) — eval-harness и
  генератор датасета — этап 6 (п. 16.6).
- **DATE_OF_BIRTH по диапазону** — кластерный слой (п. 7.6), не regex.

## 5. Остаточные риски

- **Веса ИНН/Luhn не сверены с внешним эталоном** (angryscan, Apache-2.0 + NOTICE)
  — риск R7 остаётся открытым до порта; ложные 0.99 при систематической ошибке
  в весах не обнаруживаются текущими векторами.
- **IBAN mod-97** реализован по памяти спецификации ISO 13616; независимый эталон
  (официальный реестр IBAN) не подключён — mitigация тем же портом R7.
- **Regex-подобные ложные срабатывания** форматных типов (напр. 20-значное число
  как счёт) возможны на синтетике без checksum — снижается кластерным слоем и
  ensemble (этап 3+).

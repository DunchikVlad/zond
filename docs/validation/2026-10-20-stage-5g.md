## 2. Что подтверждено тестами

**web (`internal/web/server_test.go`)**:
- Рендер всех страниц 200 со ключевым контентом: /scans (id прогона),
  /scans/{id} (источник), /verdicts (таблица), /review (путь вердикта),
  /drift, /cost, /settings (агент), /audit («Целостность hash-chain: OK»),
  статика style.css и htmx.min.js.
- `/` → 302 на /scans; CSP `default-src 'self'` в ответе.
- **Evidence-whitelist**: verdict с `Evidence{"debug":"SEKRET-RAW-VALUE"}`
  не рендерит строку в HTML; маскированный `reason` рендерится.
- Auth: без сессии → 302 `/saml/login` (без петли редиректов на /saml/*);
  viewer: GET 200, POST /scans/start → 403; admin: POST → runner.Start
  (actor — субъект сессии).
- Ревью: confirm → `confirmed` + `reviewed_by=sso:admin@example.com`;
  повторный confirm → «Конфликт» в ответе без изменения вердикта;
  bulk reject → сводка «выполнено 1», вердикт rejected.

**scheduler (`internal/scheduler/scheduler_test.go`)**:
- Прочистка кэша: просроченная запись удалена, свежая осталась, аудит
  `cache_purge` с числом удалённых.
- Retention: прогон с finished_at 100 дней назад удалён вместе с
  verdicts/agent_calls/review_events/scan_tables; сегодняшний остался;
  аудит `retention_purge` с cutoff и removed_scans.
- Невалидный cron у источника → Start не падает, аудит `invalid_schedule`.
- Per-source schedule: `@every`-выражение дергает runner (actor scheduler).

## 3. Не проверено / ограничения

- Браузерный E2E (рендеринг HTMX, своп фрагментов очереди) — только
  handler-уровень: HTMX-запросы эмулированы заголовком `HX-Request`;
  визуальная проверка и поведение htmx.min.js в браузере не выполнялись.
- CSP `default-src 'self'` без 'unsafe-inline': inline-стили/скрипты на
  страницах отсутствуют (проверено тестом заголовка); расширение CSP-политики
  под фичи (графики, shortcuts) — отдельная задача.
- Нагрузочная проверка рендеринга (большие списки вердиктов) не проводилась —
  пагинация 50/стр по построению.
- Retention audit_log не тестируется — не реализовано намеренно (append-only).

## 4. Остаточные риски

- Bulk-ревью больших очередей — последовательные транзакции, длительность
  растёт линейно; разумный предел ~сотни карточек за запрос (R9-подстройка
  порогов снизит очередь).
- Scheduler в single-instance: при serve-рестарте окно до следующего слота
  cron; ничего не пропускается критичного (purge идемпотентны).

## 2. Покрытие новых путей

**В этой сессии юнит-тесты новых путей не писались** — по указанию владельца
тестирование делает отдельный агент. Протокол того, что требует покрытия
(чек-лист для следующего агента):

- `internal/config`: `ParseWindow` — валидные форматы, `HH:MM-HH:MM` через
  полночь, отказ: без дефиса, непятибуквенные части, `start == end`,
  часы/минуты вне диапазона; `Contains` (границы включительны слева,
  исключительны справа; полночь); `NextStart` (внутри окна → now; до окна →
  сегодня; после окна → завтра; через полночь); валидация `scan_window` и
  отрицательных лимитов в `Connections.Validate`.
- `internal/scanengine`: параллельный путь (`MaxTables>0`) — breaker-серия и
  итоговые счётчики совпадают с последовательным путём на тех же данных
  (в т.ч. `overloadTables(6)` → trip на 5-й, 6-я не тронута); gate не
  превышает MaxTables одновременных таблиц; мягкая остановка (ctx) →
  `interrupted`, без ложных failed; `queryCtx` — дедлайн на запрос;
  потокобезопасность — `go test -race` с LLM-fake и кластеризацией.
- `internal/scheduler`: источник с окном — cron вне окна → `Start` не
  вызван, в аудите `scheduler/scan_deferred` (actor scheduler), по таймеру —
  `Start`; внутри окна → немедленный `Start`; `Stop()` снимает таймер.
- `cmd/zond` (runner): второй старт при занятом слоте → 502
  `source_unavailable`; слот освобождается по завершении; лимит >1 пускает
  параллельные прогоны одного источника.

## 3. Регрессионная безопасность

- Дефолты спецификации (`0` в конфиге → 1/2/300 с) применяются аксессорами —
  конфиги без новых полей ведут себя как задокументировано в п. 13.2.
- Движок при `MaxTables<=0` и `QueryTimeout<=0` — прежний последовательный
  путь без дополнительных дедлайнов (обратная совместимость тестов и CLI
  без новых полей).
- Строгая схема connections.yaml (ADR-0009): новые поля опциональны, старые
  конфиги грузятся без изменений (подтверждено `config validate`).

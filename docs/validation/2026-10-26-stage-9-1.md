## 2. Регрессионные сценарии

### `/sources`

- XSS: имя `<img …>` и ошибка в HTMX-фрагменте присутствуют только в escaped-виде.
- Секреты: `plaintext${PW}`, `${PW}plaintext`, `${PW}${OTHER}`, malformed ref
  отклонены; целые `${CH_DSN}`/`${MONGO_URI}` и Vault `ref` приняты.
- Полная схема: отсутствующий `version`, дубли имён и отрицательные лимиты
  отклоняются `ValidateAll`.
- Vault/limits round-trip сохраняет ref-only адрес и числовые YAML-поля;
  нечисловой HTTP-input не меняет файл.
- Восемь конкурентных сохранений разных источников завершились без потерь;
  временных файлов не осталось. Race-detector чист.
- Ошибка hot apply при save и delete: HTTP 500, исходный файл восстановлен.
- Закрытый store при аудите: HTTP 500, файл восстановлен, apply старого
  состояния вызван повторно.

### Qualified tables и store

- `sales.users` и `archive.users` с одинаковым путём `email` дают два независимых
  вердикта с разными ID и два чекпоинта; resume пропускает только done-схему.
- Экранирование точек и обратной косой черты проверено отдельными кейсами.
- Drift сравнивает одинаковые имена из разных схем независимо.
- Миграции: общий up/down/up и отдельный сценарий v9 → Open(v10) с уже
  существующими scan/checkpoint/verdict. Старые bare table и ID сохранены,
  provenance остался пустым; новые SaveScan получают identity version 2.

### Resume

- Совпадение provenance допускает runner.Resume и создаёт новый ID.
- Несколько одновременных несовпадений возвращаются одним списком; engine не
  создаёт новый scan после отказа. Legacy/пустые значения несовместимы.
- REST: 202 + `resume_from`, 404, 409 status, 409 `resume_incompatible`
  с двумя mismatch, 501 без runner.
- UI: кнопка у partial, POST с CSRF → 302 на новый scan. Маршруты API/UI
  используют существующие `ActionScan`/CSRF middleware.

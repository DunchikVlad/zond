# Runbook: restore from backup

## 1. Назначение
Этот runbook описывает процедуру восстановления инстанса `classifier` из backup.

Сценарии:
- повреждение SQLite Verdict Store;
- перенос инстанса;
- проверка disaster recovery;
- учебное восстановление в рамках DoD/релизного процесса.

## 2. Симптомы / поводы для восстановления
- БД не открывается;
- нарушена целостность файла БД;
- требуется поднять новый инстанс на основе последнего backup;
- требуется forensic-копия и восстановление в изолированном окружении.

## 3. Возможные причины
- повреждение файловой системы;
- неудачный деплой;
- ручное вмешательство;
- аппаратный сбой;
- нарушение целостности audit/store;
- аварийное завершение процесса с последствиями для тома.

## 4. Быстрая диагностика
Проверить:
1. есть ли актуальный backup;
2. соответствует ли backup ожидаемой версии;
3. доступен ли matching binary / migration set;
4. сохранены ли необходимые config files;
5. есть ли доступ к env / Vault / SSO metadata / reverse-proxy config;
6. нет ли признаков tampering, требующих forensic-процедуры до восстановления.

## 5. Пошаговые действия

### Шаг 1 — изолировать инцидент
Если восстановление делается после сбоя:
- остановить активный инстанс;
- зафиксировать артефакты инцидента;
- сохранить повреждённую БД отдельно;
- не перезаписывать её до завершения расследования при признаках tampering.

### Шаг 2 — подготовить целевое окружение
Подготовить:
- совместимую версию бинарника;
- директорию хранения SQLite;
- конфиги (`connections.yaml`, `detectors.yaml`, `taxonomy.yaml`);
- env / Vault access;
- reverse-proxy / TLS / SSO prerequisites.

### Шаг 3 — восстановить backup
Восстановить backup-файл в целевое место хранения.
Если используется процедура через `VACUUM INTO`, убедиться, что файл копирован полностью и без постобработки, нарушающей целостность.

### Шаг 4 — проверить миграционную совместимость
Проверить:
- версия бинарника;
- набор миграций;
- schema compatibility;
- config compatibility;
- `taxonomy_version`, если она фиксируется в данных scan/verdict provenance.

### Шаг 5 — выполнить проверку целостности
Проверить:
- SQLite открывается;
- ключевые таблицы доступны;
- `audit_log` читается;
- hash-chain сходится;
- `scans`, `verdicts`, `agent_calls` консистентны;
- нет явных ошибок foreign key / corruption.

### Шаг 6 — выполнить preflight
Запустить `doctor` / эквивалентные проверки:
- свободное место;
- доступность источников;
- доступность агентов;
- доступность секретов;
- валидность конфигов;
- доступность зависимостей SSO / TLS / DNS при необходимости.

### Шаг 7 — поднять сервис
Запустить `serve` в контролируемом режиме и проверить:
- health/readiness;
- UI/API;
- чтение scan history;
- audit access;
- базовые операции просмотра.

### Шаг 8 — зафиксировать результат
Задокументировать:
- из какого backup восстановлено;
- какая версия бинарника использована;
- прошёл ли hash-chain check;
- какие отклонения обнаружены;
- требуется ли дополнительное расследование.

## 6. Ожидаемый результат
После выполнения runbook:
- инстанс восстановлен;
- данные verdict/audit доступны;
- целостность подтверждена;
- эксплуатационные зависимости проверены;
- инцидент задокументирован.

## 7. Если не помогло
Эскалировать с приложением:
- backup identifier / timestamp
- версия бинарника
- результаты проверки SQLite
- результаты hash-chain проверки
- список недоступных зависимостей
- перечень несоответствий схемы / конфигов

## 8. Ограничения и меры предосторожности
Нельзя:
- запускать восстановленный инстанс в production без проверки hash-chain;
- смешивать backup от одной версии с произвольным бинарником без проверки миграций;
- править backup вручную;
- терять forensic-копию повреждённой БД при подозрении на tampering;
- игнорировать несовместимость config/schema/provenance.

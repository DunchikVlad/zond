# Runbook: массовый рост pending

## 1. Назначение
Сценарий: доля колонок со статусом `pending` резко выросла — в новых
сканах, на отдельном источнике или по всему контуру.

Симптомы:
- страницы `/scans/{id}` и `/review` показывают рост `pending`;
- алерт `pending_backlog` (R9: >500 pending на источник) поднят в `/alerts`;
- скан завершился `done`, но доля решённых без LLM упала (п. 17);
- очередь ревью растёт быстрее, чем команда её разбирает.

## 2. Возможные причины (п. 22.1)

1. **Дрейф данных** — в источнике появились новые форматы значений,
   которых нет в словарях/регулярках слоёв 0–1.
2. **Деградация LLM-агентов** — серия `llm_unavailable`, рост retry,
   ответы не проходят валидацию схемы → runbook `llm-unavailable.md`.
3. **Ошибка новой версии `detectors.yaml`** — hot-reload применил
   пороги/маск-профиль, уводящие каскад в серую зону: `tau_accept`
   слишком высок, `confidence_band` сместился, recognizer сломан.
4. **Mask-profile** — слишком агрессивное маскирование сломало
   распознавание (слой 1 не видит значения целиком).
5. **Новая таксономия** — `taxonomy_version` поменялась, ключи кэша
   вердиктов сменились → прежние auto-вердикты не применились (п. 10.5).

## 3. Быстрая диагностика

Команды / точки наблюдения:
- `/alerts` — открытые `pending_backlog`, `llm_unavailable`;
- `/cost` и `/scans/{id}` — сводка по слоям (доля auto_accepted,
  no_llm_share, pending по источникам);
- `audit export -category agent` — ошибки вызовов агента за окно;
- `audit export -category config` — не было ли hot-reload
  `detectors.yaml` непосредственно перед ростом (событие с diff);
- страница `/drift` — сравнение с предыдущим сканом того же источника;
- `agent-check` (и `-online` при доступном стенде).

Порядок:
1. Рост на **одном** источнике → смотрим дрейф (`/drift`) и пробы
   значений новых колонок вручную (слои 0–1 должны брать структурные
   типы без LLM).
2. Рост **по всем источникам** после смены конфигурации → diff из аудита
   config: откатить `detectors.yaml` к прежней версии (вернуть файл,
   hot-reload применит и зааудирует новый diff).
3. **Серия llm_unavailable** → runbook `llm-unavailable.md`.
4. Ничего не изменилось, данных стало больше/иных → это дрейф данных:
   расширение словарей/recognizer'ов — задача настройки на данных
   заказчика (п. 17: честные метрики в `/cost`).

## 4. Пошаговые действия

### Шаг 1 — заморозить причину, а не симптом
Зафиксировать: период, источники, `detectors_version`, `taxonomy_version`,
версию бинарника, наличие `llm_unavailable`-серий. Без этого любое
действие («пороги вниз») слепое.

### Шаг 2 — устранить LLM-причину (если она)
По runbook `llm-unavailable.md`: локальный эндпоинт, allowlist,
`offline`-режим. После восстановления перезапустить прогон источника.

### Шаг 3 — откат конфигурационной ошибки
Если рост совпал с hot-reload `detectors.yaml`: вернуть прежний файл из
VCS; watcher применит его (событие аудита с diff «было → стало»);
перезапустить прогон и сравнить долю pending.

### Шаг 4 — пороги обоснованно, а не вслепую
Если причина — данные, а не поломка: прогнать eval-harness
(`make eval` — слои 0+1; sweep порогов `tau_*` через `cmd/eval`) на
эталонном датасете и поднять пороги по его результатам, не по ощущениям.

### Шаг 5 — разбор ревью
Пока доля высока: обработать очередь `/review` (confirm/reject/relabel —
все действия аудируются, п. 14.2). Массовый reject по типу колонки
возможен через bulk-действие страницы `/review`.

## 5. Ожидаемый результат
- Причина классифицирована: дрейф данных | LLM-деградация | конфигурация;
- pending вернулся к базовой линии или осознанно принят как дрейф данных
  с планом расширения детекторов;
- изменения конфигурации зааудированы с diff (кто/когда/что).

## 6. Если не помогло
Эскалировать с: периодом роста, источниками, version tuple
(`detectors_version`, `taxonomy_version`, версия бинарника), выводом
`/cost`, открытыми алертами, diff'ами аудита config, сэмплом
нераспознанных значений (маскированным!).

## 7. Ограничения и меры предосторожности
- Не снижать `tau_accept` «на всякий случай» без eval — вырастет доля
  ложных auto_accepted (риск R1);
- не отключать маскирование ради разбора (ADR-0010);
- в выгрузках диагностики — только маскированные значения.

# Runbook: scan stuck in `running`

## 1. Назначение
Этот runbook используется, если скан долго остаётся в состоянии `running` без видимого прогресса.

Сценарии:
- scan не завершился в ожидаемое время;
- UI/API показывает `running`, но статистика не меняется;
- есть подозрение на зависание pipeline, writer или внешнего вызова.

## 2. Симптомы
Признаки проблемы:
- статус скана долго остаётся `running`;
- не увеличивается число обработанных таблиц/колонок;
- отсутствуют новые `agent_calls` или `verdicts`;
- scheduler/UI не фиксирует продвижение;
- есть таймауты к источнику или агенту, но scan не переходит в `partial`, `failed` или `interrupted`.

## 3. Возможные причины
- зависание коннектора к БД;
- зависание LLM-вызова или retry-loop;
- блокировка writer-очереди SQLite;
- ошибка координации context cancellation;
- некорректный circuit breaker / semaphore behavior;
- проблема с audit writer;
- deadlock / goroutine leak;
- внешняя деградация источника или LLM endpoint.

## 4. Быстрая диагностика
Проверить:
1. Есть ли новые записи в operational logs по этому `scan_id`.
2. Есть ли новые события в `audit_log`.
3. Обновляется ли `agent_calls`.
4. Есть ли прогресс по `scan_tables`.
5. Нет ли ошибок `SQLITE_BUSY`, timeout, context deadline exceeded.
6. Нет ли зависания на одном источнике или одной таблице.

Команды / точки наблюдения:
- логи процесса `classifier serve`
- записи по `scan_id` в `scans`
- записи по `scan_id` в `scan_tables`
- записи по `scan_id` в `agent_calls`
- health/readiness endpoints
- системные метрики процесса

## 5. Пошаговые действия

### Шаг 1 — подтвердить отсутствие прогресса
Сравнить значения:
- `scans.stats_json`
- количество `scan_tables` со статусом `done`
- число новых `verdicts`
- число новых `agent_calls`

Если данные меняются — это не зависание, а долгий scan.

### Шаг 2 — определить, где остановился pipeline
Понять, зависание произошло:
- на чтении источника,
- на сэмплировании,
- на LLM-вызовах,
- на записи в SQLite,
- на аудит-цепочке.

### Шаг 3 — проверить внешние зависимости
Проверить:
- доступность БД-источника,
- доступность LLM endpoint,
- таймауты,
- Vault/SSO не должны блокировать уже идущий scan напрямую, но могут влиять на соседние функции.

### Шаг 4 — принять решение об остановке
Если scan реально завис:
- выполнить мягкую остановку через предусмотренный API/CLI;
- зафиксировать `scan_id`, `source_id`, время, последнюю активность;
- собрать correlation id и релевантные логи.

### Шаг 5 — оценить возможность resume
После остановки проверить:
- совпадают ли `config_fingerprint`,
- `taxonomy_version`,
- версия бинарника,
- нет ли несовместимых изменений `detectors_version` / prompt behavior.

Если условия соблюдены — использовать `resume`.

## 6. Ожидаемый результат
После выполнения runbook должно быть понятно:
- это реальное зависание или просто медленный scan;
- на каком участке возникла проблема;
- можно ли безопасно остановить и возобновить scan;
- требуется ли исправление кода, конфигурации или инфраструктуры.

## 7. Если не помогло
Эскалировать с приложением:
- `scan_id`
- `source_id`
- время начала scan
- последний timestamp активности
- релевантные логи
- `agent_calls` / `scan_tables` summary
- версия бинарника
- `config_fingerprint`
- `taxonomy_version`
- `detectors_version`

## 8. Ограничения и меры предосторожности
Нельзя:
- принудительно редактировать статус scan в БД вручную без forensic-фиксации;
- отключать audit/logging ради “ускорения” диагностики;
- подменять конфиг во время анализа инцидента без фиксации изменений;
- возобновлять scan без проверки совместимости resume.

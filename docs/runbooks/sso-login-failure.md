# Runbook: проблемы SSO / вход в веб-UI

## 1. Назначение
Сценарий: пользователи не могут войти в веб-UI через SSO (SAML 2.0),
вход «зависает», ACS отвечает ошибкой, или IdP недоступен длительно и
нужен аварийный доступ.

## 2. Симптомы
- циклический редирект между `/saml/login` и IdP;
- `500` на ACS (`/saml/acs`) после ввода учётных данных;
- «доступ запрещён» после успешного входа у IdP;
- UI доступен, но сессия обрывается раньше ожидания;
- длительная недоступность IdP (инцидент у поставщика).

## 3. Возможные причины
- у IdP сменились метаданные/сертификат подписи — локальный кэш
  метаданных устарел (refresh — 24 ч, п. 11.3);
- clock skew >60 с между сервером zond и IdP — assertions отклоняются
  по временным меткам (п. 14, replay/хронология);
- рассинхрон `entity_id` / `acs_url` в connections.yaml с настройками
  клиента в IdP;
- NameID-формат или `role_attribute` не совпадают с тем, что шлёт IdP —
  пользователь входит, но без роли (viewer по умолчанию / отказ 403);
- cookie `SameSite=Lax` на http-контуре: tracked-request cookie части
  браузеров не доходит до POST ACS (п. 14.2 cookie_samesite);
- `admin_token_fallback` включён и оператор случайно шлёт
  `X-Admin-Token` — вход админским токеном, а не SSO (см. аудит);
- просрочен TLS-сертификат SP (проверяет `zond doctor`, код `tls.cert`).

## 4. Быстрая диагностика

```bash
# события входа/неудач (п. 14.2): login success/failure с причиной
zond audit export -category auth
# отказы авторизации (403: роль, ресурс)
zond audit export -category authorization
# TLS-сертификат SP и общий preflight
zond doctor [-online]
```

Плюс логи `serve` (stderr/stdout, JSON, correlation id — п. 14.1): ищем
ошибки ACS и причины отказа в строке входа.

Порядок:
1. Один пользователь или все? Один → роли/атрибуты; все → метаданные IdP,
   часы, URL'и.
2. Неудача до или после ввода пароля у IdP? До — проблема на старте
   флоу (entity_id/metadata); после — ACS (подпись, часы, cookie).
3. Совпадает ли время сервера с IdP (`date` / NTP).

## 5. Пошаговые действия

### Шаг 1 — восстановить корректность metadata
Перезапустить `serve` (метаданные IdP читаются на старте, п. 11.3) либо
дождаться 24-часового refresh; убедиться, что
`idp_metadata_url`/`idp_metadata_file` указывают на актуальные метаданные.

### Шаг 2 — сверить параметры клиента IdP
- `entity_id` и `acs_url` из connections.yaml === настройки клиента в IdP;
- сертификат подписи IdP из metadata === тому, чем подписан ответ;
- `name_id_format` и `role_attribute` соответствуют маппингу realm'а
  (демо-контур: `deploy/docker-compose.keycloak.yml` + realm-zond.json,
  атрибут `Role`).

### Шаг 3 — часы и cookie
- Свести clock skew ≤60 с (NTP на обоих концах).
- Prod за TLS: `cookie_samesite: none` + Secure; http-dev — `lax`
  (часть браузеров не шлёт tracked-cookie на POST ACS, п. 14.2).

### Шаг 4 — аварийный доступ (fallback) при длительной деградации IdP
Осторожно, п. 14.2:
1. Включить `sso.admin_token_fallback: true` в connections.yaml, задать
   `CLASSIFIER_ADMIN_TOKEN` в env инстанса (сильная случайная строка),
   рестарт `serve`.
2. Использовать токен только для аварийных действий: каждое
   использование пишет `admin_token_used` (warn) в аудит — события видны
   в `/audit` и `audit export -category auth`.
3. Отследить входы за период деградации IdP: аудит auth за интервал
   (`-since`/`-until` фильтры экспорта) — все `sso:<subject>` и
   `admin-token` действия с обоснованием.
4. После восстановления IdP — выключить fallback (рестарт), токен из env
   убрать. Использования fallback за инцидент — в отчёт об инциденте.

### Шаг 5 — массовый разлогин
Рестарт `serve` инвалидирует все in-memory сессии (п. 11.3) — при
подозрении в компрометации сессий это штатный способ принудительного
разлогина; входы после рестарта фиксируются аудитом.

## 6. Ожидаемый результат
- Вход восстановлен для всех затронутых пользователей; clock skew ≤60 с;
- использования fallback за инцидент перечислены и обоснованы;
- аудит auth за период инцидента выгружен и приложен к отчёту.

## 7. Ограничения и меры предосторожности
- Не отключать проверку подписи assertions и временных меток ради
  «завести вход» — это отказ от защиты п. 14 (replay/подмена);
- fallback не держать включённым постоянно (п. 14.2 — рекомендация);
- при подозрении на компрометацию — рестарт (разлогин всех) + ротация
  `CLASSIFIER_ADMIN_TOKEN` + аудит-разбор.

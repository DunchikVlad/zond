# Security note: этап 0 — стартовый scaffold проекта

Дата: 2026-10-18  
Исполнитель: Coordinator / Stage 0

## 1. Что изменяется
На этапе 0 создаётся базовый каркас проекта `classifier`:
- структура репозитория;
- стартовые контракты и доменные типы;
- базовые конфиги;
- CLI scaffold;
- стартовые документы по прогрессу, валидации и runbook'ам.

На этом этапе ещё не реализуются полноценные:
- вызовы LLM;
- коннекторы к БД;
- Verdict Store;
- SSO;
- аудит;
- экспорт;
- runtime-secret resolution.

## 3. Влияние на безопасность
### Данные, которые могут покидать процесс
На этапе 0 таких потоков быть не должно.

Допустимы только:
- локальная сборка;
- локальные тесты;
- чтение локальных конфигов.

Не должно быть:
- внешних LLM-вызовов;
- сетевых вызовов к БД-источникам как части scaffold;
- экспорта данных;
- передачи чувствительных значений наружу.

### Данные, которые сохраняются
На этапе 0 допускается хранение только:
- исходного кода;
- шаблонных конфигов без секретов;
- документации;
- тестовых scaffold-артефактов без реальных данных.

### Данные, которые запрещено сохранять / логировать
Запрещено:
- реальные секреты;
- API keys;
- raw PII/PCI/PHI;
- реальные DSN/URI с паролями;
- сырые sample-значения колонок;
- любые raw payloads будущих LLM-вызовов.

## 4. Проверки защитных механизмов
- Маскирование: на этапе 0 ещё не реализовано, но архитектурно должно быть изолировано в `agentproxy/mask`.
- Redact логов: на этапе 0 ещё не реализован middleware, но любые примеры в docs и конфигах должны быть без секретов.
- Audit coverage: на этапе 0 runtime-аудит не реализован; документирование изменений выполняется через `docs/`.
- RBAC / auth: ещё не реализовано.
- Egress control: на этапе scaffold не должно быть внешнего egress-поведения.
- Secrets handling: только шаблонные placeholders, без materialized secrets.

## 5. Риски
- в scaffold могут случайно попасть реальные значения в примерах конфигов;
- ранние заглушки CLI/logging могут закрепить небезопасные практики логирования;
- при быстром старте команды есть риск оставить security notes «на потом»;
- если структура пакетов будет размытой уже на этапе 0, позже сложнее удержать security boundaries.

## 6. Компенсирующие меры
- использовать только явно фиктивные значения в примерах;
- не добавлять debug-логи с потенциально чувствительными полями;
- сразу закладывать отдельные зоны ответственности для `agentproxy`, `secrets`, `audit`, `logging`;
- все security-sensitive решения фиксировать отдельными notes по мере реализации.

## 7. Вывод
Статус:
- допустимо для этапа 0;
- при переходе к этапу 1+ обязательна отдельная security-проверка на каждую зону: connectors, rules, logging, agentproxy, store, auth, audit.

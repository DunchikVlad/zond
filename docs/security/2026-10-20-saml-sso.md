# Security note: SAML SP (инкремент 5в-5, ADR-0011)

Дата: 2026-10-20
Изменение: встроенный SAML 2.0 Service Provider (crewjam/saml), SSO-флоу,
JIT-роли, аудит входов, Keycloak-стенд.

## Поверхность изменения

- Новые анонимные эндпоинты `/saml/*` (вне auth-middleware): metadata, login,
  acs, logout, slo. ACS принимает POST с SAMLResponse от IdP.
- Cookie `zond_session` (HttpOnly; Secure по схеме/TLS; SameSite из конфига:
  lax default | none для prod-https).
- JIT-записи в `users` (subject, displayName, роль) при каждом входе.
- Аудит (категория auth): `sso_login_success` (actor `sso:<subject>`),
  `sso_login_failure` (actor `sso:unknown`, только причина ≤160 символов),
  `sso_logout`, `slo`, `sso_metadata_*`, `sso_ephemeral_cert` (warn).

## Меры (blueprint п. 11.3, п. 14)

| Угроза | Мера |
|---|---|
| Подмена assertion | Подпись Response/Assertion валидируется crewjam по ключам из IdP-метаданных (KeyDescriptor); хронология (NotBefore/NotOnOrAfter, skew) — crewjam |
| Replay assertions | Проверка InResponseTo через tracked-request cookie (crewjam RequestTracker); IDP-initiated отключён (`AllowIDPInitiated=false`) |
| Фиксация сессии | Cookie HttpOnly; Secure при https; SameSite по конфигу; idle-TTL 12 ч (SessionStore); ротация id при каждом входе |
| Подделка SSO-сеанса извне | Сессия создаётся только в CreateSession после валидации assertion; cookie не читается из RelayState/параметров |
| Утечка данных через аудит/ошибки | SAMLResponse не пишется в аудит и ошибки — только типизированная причина (ADR-0010); details входа — subject и роль |
| SSRF на метаданные IdP | Загрузка только из настроенного URL/файла; таймаут 15 с; лимит 1 МБ |
| Компрометация ключей SP | Файлы из конфига (вне БД); ротация процедурой «добавить → раскатать → убрать»; ephemeral только dev |

## Принятые риски / ограничения

- **Подпись IdP-initiated LogoutRequest не валидируется** — crewjam не
  поставляет валидатор LogoutRequest; разбор минимальный (NameID). Риск:
  поддельный SLO-запрос завершит сессию субъекта (DoS деградации, не
  эскалация). Митигация: SLO принимается только на отдельном пути, источник
  ограничивается сетевыми ACL контуром; при появлении валидатора в crewjam
  или отдельной реализации — включить (отслеживается в 5г/7).
- **Ephemeral-сертификат SP** (без файлов в конфиге): подпись AuthnRequest/
  LogoutRequest ключом, которого нет в файлах конфигурации — заметен только
  warn-аудитом. Prod-чеклист (этап 7, `doctor`): sp_certificate_file обязан
  быть задан.
- **Anti-replay на IdP-initiated**: отключён по построению (нет request id);
  вход только SP-initiated — соответствует п. 14.
- **clock skew**: crewjam допускает стандартное окно (до 60 с типично) —
  зависит от настройки IdP; мониторить алертингом skew-ошибок входа.

## Чек-лист privacy-review (п. 18.2)

- Что получает: assertion (subject, атрибуты Role/displayName/email,
  группы) — только от настроенного IdP.
- Где хранит: `users` (subject, displayName, роль, last_login) и аудит
  (subject, роль) — без значений атрибутов.
- Как логируется: события auth (см. выше); операционные логи — пути/статусы.
- Чем ограничен egress: только URL метаданных IdP; никаких внешних вызовов
  из SSO-слоя, кроме него.

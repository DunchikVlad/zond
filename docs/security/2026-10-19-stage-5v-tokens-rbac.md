# Security note: этап 5, инкремент 5в (часть 1) — API-токены, RBAC, admin-token

Дата: 2026-10-19
Объект: `internal/auth`, `internal/api/auth.go`, `zond token`, store tokens.
См. ADR `docs/decisions/ADR-impl-stage-5v-tokens-rbac.md`.

## 1. Что закрыто

- **Программный доступ без SSO (п. 14.2).** API-токены со scope
  read/review/export/admin; хранение только argon2id-хэшем (утечка БД не
  раскрывает ключи; параметры OWASP t=1/m=64MiB/p=4); ключ показывается
  один раз; TTL default 90 дней; отзыв мгновенный (revoked_at проверяется
  на каждый запрос — кэша нет); `last_used_at` троттлится (1ч) против
  write-шторма на единственном соединении.
- **Авторизация по матрице п. 11.3.** viewer — только просмотр; export/
  review/scan/audit — admin (или соответствующий scope у токена).
  Просмотр аудита зарезервирован за admin (ActionAudit — пригодится /audit
  в 5г). Отказы 401/403 аудируются (auth/api_auth_failure,
  authorization/forbidden с actor/ролью/действием/путём).
- **Привязка действий к личности (п. 14.2).** Ревью пишет reviewed_by и
  review_events.actor из субъекта; старт/стоп скана и экспорт аудируются
  от sso:<subject>/token:<id>/admin-token; аудит движка скана — от имени
  инициатора (ScanRunner actor).
- **Admin-token fallback (п. 11.3).** Только env `CLASSIFIER_ADMIN_TOKEN` +
  `admin_token_fallback: true`; каждое использование — аудит warn
  (admin_token_used); отключается штатно (`false`). Невалидный Bearer НЕ
  проваливается в admin-token (нет молчаливой эскалации при опечатке).
- **Хранение сессий.** In-memory (п. 11.3): рестарт разлогинивает; id —
  crypto/rand 32 байта; TTL 12ч; cookie-имя зафиксировано (`zond_session`),
  флаги HttpOnly/SameSite=Lax/Secure — выставятся в SAML-хендлерах 5в-5
  (сейчас cookie ставить некому).

## 2. Новая поверхность и её границы

- **Перебор ключей в ResolveToken**: argon2id-сверка по каждому живому
  токену (~50 мс). DoS через навязчивые Bearer-запросы ограничен тем, что
  невалидный ключ дешевле валидного? Нет — сверка идёт по всем кандидатам
  всегда (constant-work по числу токенов, не ранний выход): нагрузка
  предсказуема и мала при единицах-десятках токенов. Rate-limit (100 req/s,
  п. 11.2) — следующий инкремент, закроет и этот вектор.
- **Timing-атака на наличие токена**: сверка constant-time по хэшу и
  constant-work по кандидатам — различить «есть такой id/префикс» нельзя
  (id в ключ не кодируется, ADR D2).
- **Токены в логах**: ключ нигде не логируется (ни при выпуске — stdout CLI,
  ни в access-логе — логируются method/path/status, без заголовков);
  в аудите — только id токена (`token:<id>`), не ключ.
- **scope admin — полный доступ**, включая старт сканов: выдавать только
  доверенным CI; ротация — issue нового + revoke старого (п. 14.2).

## 3. Открыто (владелец — 5в-5/5г)

- SAML SP (login/ACS/SLO, JIT, маппинг ролей, refresh метаданных) — часть 2.
- Rate-limit 100 req/s на субъекта (п. 11.2).
- Троттлинг неудачных попыток аутентификации (сейчас — только аудит
  api_auth_failure; брутфорс токена виден в аудите, но не замедляется).
- HttpsOnly/TLS — за reverse proxy (п. 15); Bearer-токены по открытому
  HTTP вне loopback не передавать.

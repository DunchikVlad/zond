# Security note: SIEM-sink аудит-журнала (инкремент 8-3, п. 14.2)

Дата: 2026-10-24
Изменение: опциональный внешний sink аудит-журнала в SIEM (syslog/CEF или
JSON-over-TCP) с локальной очередью и повторной отправкой — закладка
`audit_sink_state` (миграция 0009), воркер `internal/audit/sink.go`, конфиг
`audit.sink`, проверка backlog в doctor.

## Поверхность изменения

- Новый код: `internal/audit/sink.go` (воркер доставки), закладка и чтение
  журнала в `internal/audit/audit.go` (SinkEntries/SinkLastSeq/SinkAdvance/
  SinkPending), конфиг `audit.sink` в `internal/config`, wiring в serve
  (`sinkLoop`), doctor-проверка backlog.
- Новая миграция 0009 — добавляющая: таблица `audit_sink_state` (одна
  строка на инстанс). `audit_log` не меняется (триггеры append-only
  миграции 0004 нетронуты).
- Внешние эффекты: при настроенном `audit.sink` процесс serve открывает
  исходящие соединения к SIEM (TCP для json-tcp, UDP/TCP для syslog).

## Меры и свойства (blueprint п. 14, fail-closed)

| Вопрос | Ответ |
|---|---|
| Потеря событий при недоступности SIEM | Исключена по построению: очередь — сам append-only журнал; закладка двигается только за подтверждённо доставленное событие; недоставленное остаётся в журнале и догоняется повторами (Pump по тикеру) |
| Подмена/удаление журнала | Не изменилось: `audit_log` по-прежнему append-only (триггеры 0004), hash-chain; sink — только читает журнал (SELECT) и UPDATE закладки; внешний поток несёт каноническую форму — SIEM сверяет цепочку напрямую (см. runbook audit-hash-chain-broken.md) |
| Утечка через sink | На провод уходит только то, что уже в журнале: каноническая форма записи (seq/ts/actor/category/action/target/details_json). Сырые значения и секреты в журнал не попадают (ADR-0010) — sink не добавляет новых данных |
| Недоступный sink роняет аудит | Нет: запись аудита не зависит от sink (нет dual-write); воркер лишь догоняет журнал. Отказ SIEM замедляет доставку, но не журналирование (fail-closed по журналу, не по sink) |
| Порядок событий в SIEM | Строго по цепочке: воркер читает `audit_log` за закладкой `ORDER BY seq` и останавливается на первой неудаче; SIEM получает поток в порядке hash-chain — внешняя сверка цепочки корректна |
| DoS через конфиг sink | `audit.sink` валидируется при загрузке (fail-fast): kind/address обязательны вместе, address — host:port; коннект/запись с дедлайнами (3 с/5 с); ошибка сети — в лог и `last_error` закладки, цикл продолжается |
| Отставание (backlog) | Видно в doctor (`audit.sink`, WARN при недоставленном хвосте) и в закладке (`last_seq`, `last_error`, `updated_at`) |

## Принятые риски / ограничения

- **Доставка «at-least-once»**: при сбое после записи в сокет, но до
  продвижения закладки возможна дупликация одной записи на стороне SIEM
  (повторная доставка после восстановления). Приёмник обязан
  дедуплицировать по `seq` (присутствует в канонической форме и CEF).
  Идемпотентность по seq — часть контракта sink (п. 14.2 не требует
  exactly-once; требует «потеря недопустима»).
- **Одна точка доставки**: single-instance (ADR-0014) — воркер один на
  процесс serve; при рестарте закладка в БД (доставка продолжится с неё).
- **UDP для syslog** — без подтверждения: «доставлено» = «записано в
  сокет». Это осознанный компромисс протокола syslog; гарантия «не потерять
  на стороне zond» (закладка) сохраняется, потеря в сети UDP — свойство
  транспорта (выбирается оператором; для гарантии — json-tcp/syslog-tcp).
- **Backlog без лимита роста**: журнал растёт при длительной недоступности
  SIEM — ретенция журнала отдельная (п. 15.4, ≥180 дней либо выгрузка в
  SIEM; автоудаление audit_log не автоматизируется, ADR-impl-5г D3).

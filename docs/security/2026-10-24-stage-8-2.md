# Security note: per-source лимиты и окна сканирования (инкремент 8-2, п. 13.2)

Дата: 2026-10-24
Изменение: поля источника `max_concurrent_scans`/`max_concurrent_tables`/
`query_timeout_s`/`scan_window` в connections.yaml; пул воркеров таблиц в
scanengine (потокобезопасность состояния прогона); семафор сканов в
serve-runner; откладывание пересканов шедулером до начала окна.

## Поверхность изменения

- Новый код: `internal/config/window.go`, `internal/scanengine/tablegate.go`,
  `internal/scanengine/tablestate.go`; правки `scanengine/engine.go`
  (параллельные воркеры, мьютексы, дедлайны запросов), `scheduler`
  (таймеры откладывания), `cmd/zond/main.go` (семафоры источника).
- Миграций нет. Схема connections.yaml расширена опциональными полями
  (строгая схема ADR-0009: неизвестные ключи по-прежнему отклоняются).
- Внешние эффекты: старт скана сверх лимита источника отклоняется 502;
  перескан вне окна не стартует немедленно (откладывается с аудитом);
  запросы к БД ограничены дедлайном источника.

## Меры и свойства (blueprint п. 14, fail-closed)

| Вопрос | Ответ |
|---|---|
| Утечка данных через конкурентность | Разделяемое состояние прогона под мьютексами (кластерер, статистика, бюджет, прайс-кэш); буферы вызовов/аудита — локальные на таблицу (`tableState`), коммит — прежняя транзакция п. 13 (вердикты+вызовы+аудит атомарно); `go test -race ./...` зелёный |
| Может ли параллелизм обойти budget-стоп (п. 10.4)? | Нет: начисление стоимости и флаг `budgetExceeded` под общим мьютексом; проверка перед каждым LLM-вызовом; превышение возможно на ≤ (воркеры − 1) параллельных вызовов — допустимая граница семафоров LLM-gate (та же семантика гонки была у семафора п. 10.4) |
| Может ли оператор обойти окно? | Окно ограничивает только шедулер (буква спецификации: «старт вне окна откладывается шедулером»). Ручной старт (API с auth/CLI) — осознанное действие оператора, аудируется как обычно (`scan_start` с actor). Обход окна шедулером невозможен: при срабатывании таймера окно проверяется повторно |
| Злоупотребление лимитом сканов (DoS через 502) | Отказ — до подключения к источнику и создания строки `scans` (действие не совершено, аудит не засоряется); эндпоинт старта требует права scan (RBAC п. 11.3) |
| Секреты в новых полях | Лимиты/окно — числа и строка формата; секретов нет (прецедент п. 12: connections.yaml без секретов); интерполяция `${ENV}` в новых полях не требуется (не строки адресов) |
| Аудит | Откладывание — `scheduler/scan_deferred` (actor scheduler, п. 14.2 «фоновые задачи журналируются»); отказ по лимиту сканов аудита не требует (действие не начато — прецедент отказа breaker'а S8-1) |
| Дедлайн запроса vs отмена прогона | Дочерний `queryCtx` наследует родительский ctx: stop прогона работает; дедлайн классифицируется как retryable/overload (S8-1) — серия таймаутов трипает breaker, что соответствует смыслу п. 13.2 (источник не успевает = перегрузка) |

## Принятые риски / ограничения

- **Дефолт `max_concurrent_tables=2` меняет профиль нагрузки** сканов по
  умолчанию (было строго последовательно): до 2 параллельных запросов к
  источнику от одного прогона. Это зафиксированный дефолт спецификации
  п. 13.2; смягчение — `max_concurrent_tables: 1` в записи источника.
- **Семафоры/окна — состояние процесса** (как breaker, ADR-impl S8-1 D1):
  рестарт serve снимает отложенные старты и сбрасывает слоты; перескан
  повторится по cron-расписанию (деградация безопасна).
- **DST**: окно считается в локальном времени инстанса (как cron robfig);
  переход на летнее/зимнее время может сдвинуть старт на час — принимается
  (окна ночные, погрешность некритична).
- **Юнит-тесты новых путей — отдельной задачей** (см. validation
  2026-10-24-stage-8-2, раздел 2): до их появления гарантии опираются на
  статические ворота, race-прогон и регрессию существующих тестов.

# Security note: этап 5, инкремент 5б — REST API v1

Дата: 2026-10-19
Объект: `internal/api`, `zond serve`, `store.ApplyReview`, экспорт,
движок (interrupted). См. `docs/progress/2026-10-19-stage-5b-rest-api.md`,
ADR D1–D10.

## 1. Главное изменение поверхности атаки

Инкремент впервые поднимает сетевой входной адаптер: HTTP-сервер с
мутациями (старт/стоп сканов, ревью) и выгрузкой данных (экспорт). До
появления SSO (инкремент 5в) аутентификации **нет** — это осознанное,
зафиксированное в ADR D1 отклонение от п. 11.2 с компенсирующей мерой:
**`-addr` по умолчанию `127.0.0.1:8080`**. Вынос на внешний интерфейс до
5в = открытый доступ к старту сканов и выгрузке вердиктов любому, кто
достучится до порта. Не делать этого вне dev-контура; в usage `zond serve`
причина loopback-дефолта указана явно.

## 2. Что сделано для безопасности

- **Аудит всех мутаций и экспорта (п. 14.2, fail-closed).** Ревью пишет
  аудит в одной транзакции с доменным изменением (откат = ни действия, ни
  записи); stop аудируется до отмены; экспорт аудируется до выдачи данных,
  причём отказанный лимитом экспорт НЕ записывается как совершённый
  (иначе аудит врёт). Actor `api` — зарезервированный формат до
  `sso:<subject>`/`token:<id>` (5в).
- **review_events — append-only** (триггеры, паттерн audit_log): история
  ревью не переписывается даже при прямом доступе приложения к БД.
- **Evidence в ответах уже маскирован** (ADR-0010): API отдаёт то, что
  записано в store, — сырые значения в store не попадают (маскирование на
  пути сэмплера/Agent Proxy), поэтому ни вердикты, ни CSV/JSON-экспорт
  сырых значений не содержат. Отдельного слоя маскирования в API нет — и
  не нужно: маскировать надо на записи, а не на каждом чтении.
- **SQL-инъекции:** все фильтры — параметризованные запросы (`?`), без
  конкатенации пользовательского ввода; table-фильтр — LIKE с экранированием
  параметром, порядок/лимиты — из валидированных enum/чисел.
- **Валидация ввода:** action ревью — enum; label обязателен для relabel;
  min_conf ∈ [0,1]; limit/offset — неотрицательные целые с верхней границей
  (MaxPageLimit=500); format экспорта — csv|json; since — RFC3339. Любой
  мусор → 400 в едином конверте, без утечки внутренних деталей (500 отдаёт
  «внутренняя ошибка» + лог с correlation id, тело без стека).
- **ReadHeaderTimeout 10s** на HTTP-сервере (slowloris); тело запросов —
  маленькие JSON (старт/ревью), читаются одним Decode.
- **Readiness не разглашает внутренности:** `/api/ready` — только
  `{"status":"ready|not_ready"}`, детали ошибки — в лог.
- **Correlation id принимается из заголовка** как есть — только в лог и
  echo-заголовок, не в БД/аудит-детали: лог-инъекция через X-Request-ID
  невозможна в структурированном slog (значение — JSON-строка).

## 3. Открытые вопросы (владелец — инкремент 5в/5г)

- Аутентификация/авторизация: SSO-сессии, RBAC-матрица п. 11.3 (export,
  ревью, старт/стоп — admin), API-токены со scope, события
  auth/authorization, rate-limit 100 req/s на субъекта.
- Async-экспорт сверх лимита: результат по ссылке — потребует одноразовых
  ссылок/токенов скачивания и retention файлов.
- `zond serve` не умеет TLS: до внешнего контура — за reverse proxy
  (nginx/ingress, п. 15 деплой), либо встроенный TLS в этапе харденинга.
- CORS: UI server-rendered с того же origin (п. 11.3) — CORS-заголовки не
  нужны и не выставляются; если появится внешний SPA-клиент — явная политика.

# Документация проекта `classifier`

Этот каталог содержит **рабочую инженерную документацию**, которая ведётся параллельно с разработкой. Документация здесь не является вторичной: она служит инструментом управления разработкой, валидацией, безопасностью и эксплуатацией.

## 1. Источники истины

Главные документы проекта находятся в корне репозитория:

- `blueprint.md` — **единственный источник правды** по продукту, ADR, контрактам, NFR, рискам, этапам и DoD.
- `architecture.md` — производный документ, описывающий модель реализации: слои, пакеты, потоки исполнения, process model и точки расширения.

Если между документами есть противоречие, приоритет всегда у `blueprint.md`.

## 2. Назначение каталога `docs/`

Каталог `docs/` нужен для того, чтобы в ходе разработки фиксировать:
- прогресс по задачам и этапам;
- результаты валидации;
- инженерные решения;
- security notes;
- эксплуатационные runbook'и;
- ограничения, допущения и незакрытые вопросы.

Это особенно важно для multi-agent разработки: каждый агент должен не только изменять код, но и оставлять понятный инженерный след.

## 3. Структура каталога

### `docs/progress/`
Журнал прогресса по этапам и задачам.

Содержит:
- цель задачи;
- основание в `blueprint.md` / `architecture.md`;
- объём работ;
- изменённые файлы;
- ключевые решения;
- допущения и ограничения;
- проверки;
- следующие шаги.

Пример:
- `docs/progress/2026-10-18-stage-0.md`

### `docs/validation/`
Заметки по технической валидации.

Содержит:
- что валидировалось;
- какие команды/проверки запускались;
- что подтверждено;
- что не проверено;
- остаточные риски.

Пример:
- `docs/validation/2026-10-18-stage-0.md`

### `docs/decisions/`
Локальные инженерные решения и ADR-lite записи.

Используется, когда:
- нужно зафиксировать важный implementation choice;
- требуется задокументировать отклонённые альтернативы;
- нужно оставить traceable-обоснование для следующего этапа.

Пример:
- `docs/decisions/ADR-impl-stage-0-scaffold.md`

### `docs/security/`
Security notes по изменениям, влияющим на:
- masking;
- logging/redaction;
- auth/RBAC;
- audit;
- secrets;
- exports;
- egress;
- privacy / data governance.

Пример:
- `docs/security/2026-10-18-stage-0.md`

### `docs/runbooks/`
Эксплуатационные сценарии и инструкции реагирования.

Содержит пошаговые runbook'и для ситуаций вроде:
- зависший scan;
- недоступность LLM;
- restore из backup;
- разрыв audit hash-chain.

Примеры:
- `docs/runbooks/scan-stuck-running.md`
- `docs/runbooks/llm-unavailable.md`
- `docs/runbooks/restore-from-backup.md`
- `docs/runbooks/audit-hash-chain-broken.md`

## 4. Правила ведения документации

### 4.1 Документация обязательна
Любое значимое изменение в проекте должно сопровождаться обновлением хотя бы одного из видов документации в `docs/`.

Минимум, который должен появляться по важной задаче:
- запись в `progress/`;
- запись в `validation/`;
- при необходимости — `security/`, `decisions/`, `runbooks/`.

### 4.2 Язык
- Инструкции для агентов могут быть на английском.
- Вся рабочая документация в `docs/` ведётся **на русском языке**.
- Имена файлов, путей, пакетов, API и технических идентификаторов остаются на английском.

### 4.3 Документация должна быть практической
Нельзя писать формальные или пустые заметки “для галочки”.

Каждый документ должен отвечать на реальные инженерные вопросы:
- что сделано;
- почему;
- на каком основании;
- как проверено;
- какие есть риски;
- что делать дальше.

### 4.4 Нельзя откладывать документацию “на потом”
Документация ведётся одновременно с изменениями в коде, а не после релиза.

## 5. Как использовать `docs/` в multi-agent разработке

### Coordinator
Главный агент обязан:
- ссылаться на `blueprint.md` и `architecture.md`;
- раздавать подзадачи с точным scope;
- требовать у sub-agent'ов обновления docs;
- проверять, что изменения и документация согласованы.

### Implementation Agent
Агент-исполнитель обязан:
- работать только в пределах выделенного scope;
- документировать сделанные шаги;
- фиксировать допущения;
- указывать, что проверено, а что нет.

### Reviewer / QA Agent
Ревью-агент обязан проверять не только код, но и:
- полноту документации;
- security implications;
- migration/compatibility impact;
- наличие validation evidence.

## 6. Когда какой документ обновлять

| Ситуация | Что обновлять |
|---|---|
| Новая задача / этап | `progress/` |
| Выполнены проверки | `validation/` |
| Принято нетривиальное инженерное решение | `decisions/` |
| Изменение затрагивает безопасность / данные / доступ | `security/` |
| Добавлен или изменён эксплуатационный сценарий | `runbooks/` |

## 7. Базовый workflow

Рекомендуемый порядок работы:

1. Прочитать релевантные разделы `blueprint.md` и `architecture.md`.
2. Создать или обновить запись в `progress/`.
3. Выполнить изменение в коде.
4. Зафиксировать проверки в `validation/`.
5. При необходимости обновить `security/`, `decisions/`, `runbooks/`.
6. Подготовить русский итоговый отчёт.

## 9. Naming convention для документации

Чтобы несколько агентов работали единообразно, для всех документов в `docs/` действует обязательная схема именования.

### 9.1 Общие правила
- Имена файлов — только в `kebab-case`.
- Дата в начале имени файла — в формате `YYYY-MM-DD`, если документ привязан ко времени выполнения.
- Не использовать пробелы, кириллицу, `final`, `new`, `tmp`, `misc`, `notes2` и другие неинформативные суффиксы.
- Название должно отражать **суть задачи или инцидента**, а не имя исполнителя.
- Один документ = одна основная тема. Не смешивать несколько несвязанных задач в одном файле.

### 9.2 Обязательные шаблоны имён

#### `docs/progress/`
Использовать:
- `YYYY-MM-DD-<topic>.md`
- `YYYY-MM-DD-stage-<n>.md`
- `YYYY-MM-DD-<feature>-progress.md`

Примеры:
- `2026-10-18-stage-0.md`
- `2026-10-21-clickhouse-vertical-slice.md`
- `2026-10-25-agentproxy-progress.md`

#### `docs/validation/`
Использовать:
- `YYYY-MM-DD-<topic>.md`
- `YYYY-MM-DD-<feature>-validation.md`
- `YYYY-MM-DD-migration-<topic>.md`

Примеры:
- `2026-10-18-stage-0.md`
- `2026-10-25-agentproxy-validation.md`
- `2026-10-28-migration-verdict-store.md`

#### `docs/security/`
Использовать:
- `YYYY-MM-DD-<topic>.md`
- `YYYY-MM-DD-<feature>-security.md`

Примеры:
- `2026-10-18-stage-0.md`
- `2026-10-30-agentproxy-security.md`
- `2026-11-02-export-security.md`

#### `docs/decisions/`
Использовать:
- `ADR-impl-<topic>.md`
- `ADR-ops-<topic>.md`
- `ADR-security-<topic>.md`

Примеры:
- `ADR-impl-stage-0-scaffold.md`
- `ADR-security-export-policy.md`
- `ADR-ops-backup-restore-strategy.md`

Если решение заменено новым, старый файл не переименовывается хаотично: в его статусе фиксируется `superseded`, а новый документ создаётся отдельно.

#### `docs/runbooks/`
Использовать:
- `<incident-or-scenario>.md`
- `<subsystem>-<problem>.md`

Примеры:
- `scan-stuck-running.md`
- `llm-unavailable.md`
- `restore-from-backup.md`
- `audit-hash-chain-broken.md`
- `sso-login-failure.md`
- `vault-secret-resolution-failed.md`

Runbook должен описывать **сценарий**, а не дату создания.

### 9.3 Именование тем (`<topic>`)
Тема должна быть короткой и стабильной. Предпочтительный порядок слов:
- `<subsystem>-<action>`
- `<feature>-<state>`
- `<component>-<change-type>`

Хорошо:
- `agentproxy-validation`
- `verdict-store-migration`
- `clickhouse-vertical-slice`
- `taxonomy-versioning`

Плохо:
- `stuff`
- `fixes`
- `important-update`
- `new-doc`
- `misc-notes`

### 9.4 Версионирование документов
- Для progress/validation/security файлов новая значимая итерация обычно оформляется **новым файлом с новой датой**, а не бесконечным переименованием старого.
- Для runbook'ов и decision records используется **стабильное имя**, а история отражается внутри документа через статус, дату и связанные изменения.
- Если документ отражает milestone или этап, имя должно оставаться стабильным и понятным для поиска.

### 9.5 Обязательность соблюдения
Эта naming convention обязательна для всех агентов.

Если агент создаёт документ с нарушением схемы:
- документ должен быть переименован до завершения задачи;
- задача не считается полностью завершённой с точки зрения documentation hygiene.

## 10. Дальнейшее развитие документации

По мере реализации проекта желательно добавить:
- заметки по миграциям;
- документацию по provenance/versioning;
- runbook'и по SSO/Vault/doctor;
- notes по eval и benchmark;
- changelog эксплуатационных изменений.

## 11. Короткое правило

Если в проекте произошло значимое изменение, а в `docs/` не появилось понятного инженерного следа — задача считается незавершённой.
